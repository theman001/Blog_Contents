# 1. 카카오톡 모바일 기기 등록(Device Registration) 프로토콜 디버깅 보고서

## 1. 개요
이 보고서는 카카오톡의 안드로이드 API를 사용하여 PC 환경(Python 스크립트)에서 모바일 기기 등록 절차를 수행하려는 과정과 그 결과를 정리한 것입니다. 현재 `Status -100` (기기 미등록) 상태까지 로그인하는데 성공했으나, 인증 번호(Passcode) 요청 단계에서 서버 응답 오류(`-500`, `-400`)가 발생하고 있습니다.

## 2. 현재 상황 요약
| 단계 | 엔드포인트 | 결과 | 상태 코드 | 설명 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 로그인** | `login.json` | **성공** | `200` (`status: -100`) | 아이디/비밀번호 검증 성공. 기기 등록 필요 상태 반환. |
| **2. 인증 요청** | `request_passcode.json` | **실패** | `200` (`status: -500`) | 서버 내부 오류(파라미터 불충분 의심, Form-Data) |
| **2. 인증 요청** | `request_passcode.json` | **실패** | `200` (`status: -400`) | 잘못된 요청(파라미터 포맷 오류 의심, Snake-Case) |
| **2. 인증 요청** | `request_passcode.json` | **실패** | `415` | Unsupported Media Type (JSON Body 사용 시 발생) |

## 3. 상세 분석 결과

### 1. 로그인 (`/android/account/login.json`)
- **요청 방식**: `POST`, `application/x-www-form-urlencoded`
- **헤더**: `X-VC`, `Device-Info`, `User-Agent` (Android 14 에뮬레이션), `A`, `C` 헤더 필수.
- **결과**: `{"status": -100, "serverTime": ...}`
- **의미**: 인증 정보는 유효하나, 해당 `device_uuid`가 카카오 서버에 등록되지 않은 기기임. 이 응답은 정상적인 기기 등록 프로세스의 시작점입니다.

### 2. 인증 번호 요청 (`/android/account/request_passcode.json`)
디컴파일된 코드(`CreateAccountService`, `AccountRegistrationService`)를 분석하여 여러 가지 페이로드 조합을 시도했습니다.

#### 시도 1: JSON Payload + camelCase (V4, V6)
- **페이로드**: `{"countryCode": "82", ...}`
- **결과**: **415 Unsupported Media Type**
- **원인**: 서버가 `application/json` Content-Type을 허용하지 않음. `retrofit` 인터페이스에는 `@InterfaceC52276k({"Content-Type: application/json"})` 어노테이션이 있는 경우도 있었으나, 실제 엔드포인트 설정은 Form-Data를 요구하는 것으로 보임.

#### 시도 2: Form-Encoded + camelCase (V6 재시도)
- **페이로드**: `countryCode=82&countryIso=kr&phoneNumber=010...`
- **결과**: `{"status": -500}`
- **분석**: `-500`은 보통 서버 내부 에러를 의미하지만, 필수 파라미터가 누락되었거나 데이터 타입이 맞지 않을 때도 발생합니다. `PhoneNumberParams` 객체 필드명이 `snake_case`로 매핑될 가능성이 존재합니다.

#### 시도 3: Form-Encoded + snake_case + 로그인 정보 포함 (V5)
- **페이로드**: `email=...&password=...&country_code=82&phone_number=010...`
- **결과**: `{"status": -400}`
- **분석**: `-400`은 Bad Request입니다. 이는 파라미터 이름은 서버가 인식했으나, 값의 유효성이나 포맷이 틀렸을 때 발생합니다. 예를 들어, 이미 가입된 전화번호이거나, 세션 쿠키 문제일 수 있습니다.
- **특이사항**: 로그인 정보(`email`/`pw`)를 같이 보냈을 때 `-400`이 떴다는 것은, 이 엔드포인트가 로그인 정보와 무관하게 동작하거나(세션 의존), 혹은 파라미터 충돌이 있었을 수 있습니다.

### 3. 디컴파일 코드 재분석 및 V9 테스트 결과
`PhoneNumberParams` 분석 결과와 `p416Gd.C9307c`의 호출 로직을 바탕으로 V9 테스트(`register_device_v9.py`)를 수행했습니다.

#### 발견된 핵심 로직
1.  **X-VC 헤더 생성**: `request_passcode` 요청 시 `X-VC` 헤더는 이메일이 아닌 **전화번호**(`phoneNumber`)를 사용하여 생성해야 합니다. (`C13555g.a.m11141a(phoneNumber)`)
2.  **파라미터 전송**: `CreateAccountService` 메서드 호출 시 `PhoneNumberParams` 객체가 사용됩니다. JSON (`-415` 오류)이 아닌 **Form-UrlEncoded** (`-500` 오류) 방식이 서버에서 수락됩니다.

#### V9 테스트 결과 (Form-Encoded + Snake-Case + Phone-based X-VC)
- **Status**: 200 OK
- **Body**: `{"status": -500}`
- **분석**: `X-VC` 생성 로직을 수정하고 파라미터 키를 `snake_case`로 맞추었음에도 불구하고 여전히 서버 내부 오류가 발생합니다. 이는 단순 파라미터 불일치가 아니라, **보안적인 필수 선행 조건(Native Crypto, Integrity Check)** 이 누락되었을 가능성을 강력하게 시사합니다. 특히 `PhoneNumberParams`에 포함된 `codes` 리스트나 `C13555g` 외의 추가적인 헤더 검증이 있을 수 있습니다.

## 4. 결론 및 향후 계획 (Technical Roadmap)

### 4.1 결론
현재 `-500` 오류는 Python 스크립트 수준의 파라미터 튜닝으로는 해결이 어려운 **보안 장벽**에 부딪힌 상태입니다. `libtalkand_aes` 또는 `libNSaferJNI`를 통한 네이티브 암호화가 단순히 파라미터를 암호화하는 것을 넘어, 앱의 무결성을 증명하는 토큰을 생성하는 데 관여하고 있을 가능성이 높습니다.

### 4.2 향후 수행해야 할 작업
1.  **동적 분석(Frida/Hooking) 전환**: 정적 분석만으로는 서버가 기대하는 정확한 패킷 형태(특히 암호화된 값이나 숨겨진 헤더)를 파악하기 어렵습니다. 실제 안드로이드 기기나 에뮬레이터에서 카카오톡 앱을 실행하고, **Frida**를 사용하여 `CreateAccountService`가 호출될 때의 **실제 파라미터 값과 헤더**를 훅킹(Hooking)하여 캡처해야 합니다.
2.  **Native 함수 Hooking**: `libtalkand_aes.so`의 `encrypt` 함수나 `libNSaferJNI.so`의 `N_1Encrypt` 함수를 훅킹하여, **언제, 어떤 데이터가 암호화되는지** 실시간으로 관찰해야 합니다.
3.  **패킷 캡처(Packet Capture)**: HTTP Toolkit, Charles Proxy, 또는 Wireshark를 사용하여(SSL pinning 우회 필요) 실제 앱이 보내는 `request_passcode.json` 요청의 Raw Packet을 확보해야 합니다. 이는 정답지(Answer Key) 역할을 할 것입니다.

# 2. 카카오톡 안드로이드 인증 로직 구현 기술 보고서

## 1. 개요
본 보고서는 카카오톡 안드로이드 클라이언트(`v10.7.2` 이상 추정)의 인증 로직을 리버스 엔지니어링하여 분석한 결과를 기술합니다. 특히 기기 등록(Device Registration) 과정 중 인증 번호 발송이 실패하는 원인을 파악하고, 향후 심층 분석을 위해 필요한 네이티브 라이브러리 분석 대상을 식별합니다.

## 2. JADX 정적 분석 결과

### 2.1 주요 서비스 인터페이스
#### `AccountRegistrationService` & `CreateAccountService`
이 서비스들은 계정 생성 및 기기 등록과 관련된 HTTP 요청을 처리합니다.
- **`request_passcode.json`**: 인증 번호(Passcode)를 요청하는 엔드포인트입니다.
- **`PhoneNumberParams`**: 위 요청의 파라미터를 캡슐화하는 데이터 클래스입니다.

### 2.2 `PhoneNumberParams` 구조 분석
`PhoneNumberParams` 클래스의 디컴파일 결과, 다음과 같은 필드를 가지며 이는 Retrofit/Kotlin Serialization을 통해 JSON 혹은 Form-Data로 변환됩니다.

| 필드명 (Obfuscated) | 의미 (Estimated) | 필수 여부 | 비고 |
| :--- | :--- | :--- | :--- |
| `f160206a` | `countryCode` | **Yes** | 국가 코드 (예: "82") |
| `f160207b` | `countryIso` | **Yes** | 국가 ISO 코드 (예: "kr") |
| `f160208c` | `phoneNumber` | **Yes** | 전화번호 (예: "01012345678") |
| `f160209d` | `voiceCallLanguage` | No | 보이스콜 언어 (예: "ko") |
| `f160210e` | `codes` | No | 특수 코드 리스트 |

**중요 발견**:
`PhoneNumberParams`의 `toString()` 메서드는 `"PhoneNumberParams(countryCode=..., countryIso=..., phoneNumber=...)"` 형태를 반환합니다. 이는 직렬화 시 사용되는 키 이름이 **camelCase**임을 강력하게 시사합니다. 하지만 이전 테스트에서 `snake_case`로 요청 시 `-400` (Bad Request) 응답을 받았고, `camelCase` 요청 시 `-500` (Internal Server Error) 혹은 `415` (Unsupported Media Type) 응답을 받았습니다. 이는 단순 키 이름 문제 외에 **Content-Type** 혹은 **숨겨진 필수 파라미터**가 존재함을 의미합니다.

### 2.3 `System.loadLibrary` 분석
`JADX` 검색 결과, 앱의 핵심 기능은 다음과 같은 네이티브 라이브러리에 의존하고 있습니다. 특히 암호화 및 무결성 검증, 보안 통신과 관련된 라이브러리가 식별되었습니다.

## 3. GHIDRA 분석 대상 (Native Libraries)
`app/kakaotalk_apk_jadxExport` 내에서 추출된 `.so` 파일 중, 인증 및 보안 로직과 직접적으로 연관된 파일들은 다음과 같습니다.

### **최우선 분석 대상**
1.  **`libtalkand_aes_v11.3.0.so`**
    - **이유**: 파일명(`talkand_aes`)에서 알 수 있듯이, 카카오톡의 AES 암호화 로직을 포함하고 있을 가능성이 가장 높습니다. 이전 분석에서 로컬 DB 암호화나 특정 파라미터 암호화에 사용되는 것으로 추정되었습니다.
    - **위치**: `app\src\main\config.armeabi_v7a.apk\lib\armeabi-v7a\libtalkand_aes_v11.3.0.so`

2.  **`libNSaferJNI.so`**
    - **이유**: `NSafer`는 보안(Safeguard) 관련 모듈로 추정되며, 앱 무결성 검사나 루팅 탐지, 요청 서명 생성에 관여할 수 있습니다.
    - **위치**: `app\src\main\config.armeabi_v7a.apk\lib\armeabi-v7a\libNSaferJNI.so`

### **차순위 분석 대상**
3.  **`libACExternalCore.so`**
    - **이유**: `AC` (Access Control 또는 Account Control) 관련 코어 로직일 가능성이 있으며, 계정 인증 흐름에 관여할 수 있습니다.
4.  **`libDSToolkitV30Jni.so`**
    - **이유**: `DSToolkit`은 DreamSecurity의 보안 툴킷일 가능성이 높습니다. (PKI, 인증서 관련)

## 4. GHIDRA 상세 분석 결과 (`libtalkand_aes_v11.3.0.so`)
Ghidra를 통해 `libtalkand_aes_v11.3.0.so`를 분석하였으며, 주요 암호화 엔트리포인트를 식별했습니다.

### 4.1 주요 함수: `Java_com_kakao_talk_aes_TalkHello_encrypt`
- **주소**: `0x0001db54` (ARM)
- **기능**: JNI를 통해 호출되는 메인 암호화 함수입니다.
- **알고리즘**: AES-128-CBC 또는 AES-256-CBC (키 길이에 따라 결정, 256비트 유력)
- **패딩**: PKCS#7 Padding (`0x10 - (len % 0x10)`) 적용 확인.
- **키 관리**: 코드 내에 하드코딩된 정적 키(Static Key)를 사용합니다.

### 4.2 추출된 정적 키 (Static Constants)
함수 내부(`FUN_0001c260`)에서 사용되는 키와 IV(Initialization Vector) 후보를 추출했습니다.

**Candidate Key (Little Endian):**
```text
36 b4 17 d3 2a dd 44 ed a9 5b c6 47 c0 39 ea 22
(AES-256일 경우 추가: 3a 0e 4b 20 2b 54 15 43 24 34 5a 1a 51 09 40 47)
```

**Candidate IV (Little Endian):**
```text
c5 a0 6c b4 0a aa e4 9a 57 3c 2f df ab 70 64 28
```

### 4.3 시사점
이 함수(`TalkHello`)는 이름에서 유추할 수 있듯이, 최초 핸드쉐이크나 세션 키 교환 시 사용될 가능성이 높습니다. `request_passcode` API 호출 시 파라미터가 암호화되어 전송되어야 한다면(예: `-500` 에러의 원인이 암호화된 본문을 서버가 복호화하지 못해서라면), 이 키를 사용하여 파라미터를 암호화 시도해볼 수 있습니다.

### 4.3 `libNSaferJNI.so` 분석 결과
`libNSaferJNI.so`는 엔에스에이치씨(NSHC)의 보안 솔루션으로 보이며, 범용 암호화 인터페이스를 제공합니다.

- **주요 기능**: AES, SEED, ARIA, SHA 등 다양한 알고리즘 지원.
- **키 관리**: `libtalkand_aes`와 달리 정적 키를 내장하고 있지 않으며, `N_1Init`, `N_1Encrypt` 등을 통해 외부(Java Layer)에서 주입된 키를 사용합니다.
- **연관성**: `N_1Encrypt`에서 키 길이를 16바이트(AES-128)로 제한하는 로직이 발견되었습니다. 하지만 초기 인증/핸드쉐이크보다는 앱 실행 후 일반적인 데이터 보호나 무결성 검증에 사용될 가능성이 높습니다.
- **결론**: `request_passcode` 실패 분석에 있어서는 우선순위가 낮으며, `libtalkand_aes`의 정적 키 방식이 더 유력한 "신규 기기 등록"용 암호화 수단으로 판단됩니다.

## 5. 결론 및 향후 계획 (Technical Roadmap)
1.  **네이티브 암호화 검증**: Python 스크립트(`register_device_v7.py`)를 작성하여 `libtalkand_aes`에서 추출된 키와 IV를 사용해 `phoneNumber` 등의 파라미터를 AES-256-CBC (또는 128)로 암호화하여 전송 테스트를 진행합니다.
2.  **파라미터 조합 테스트**: V6에서 확인된 Form-Encoded 방식을 유지하되, 파라미터를 암호화된 값으로 대체하거나 혹은 `voiceCallLanguage` 등 누락 가능성이 있는 필드를 추가하여 `-500` 오류 해결을 시도합니다.

# 3. 카카오톡 Android 인증 프로토콜 심층 기술 분석 보고서

## 1. 개요
본 문서는 카카오톡 Android 애플리케이션의 기기 등록 및 사용자 인증 과정에 대한 리버스 엔지니어링 분석 결과를 기술합니다. JADX를 이용한 정적 분석, Ghidra를 이용한 네이티브 라이브러리 분석, 그리고 Python을 이용한 프로토콜 에뮬레이션 테스트 결과를 종합하여 작성되었습니다. 본 보고서는 향후 클라이언트 구현을 위한 기술 명세서로 활용될 수 있습니다.

## 2. 인증 및 기기 등록 프로세스 (Authentication Flow)

전체적인 기기 등록 프로세스는 다음과 같은 순서로 진행됩니다.

1.  **로그인 (`/login.json`)**: 이메일/비밀번호 검증 및 초기 세션 수립.
2.  **인증번호 요청 (`/request_passcode.json`)**: 미등록 기기일 경우 SMS/ARS 인증 시도.
3.  **기기 등록 (`/register_device.json`)**: 수신된 인증번호를 전송하여 기기 등록 완료.

## 3. API 상세 명세 및 데이터 구조

모든 API 요청은 공통적으로 다음 헤더를 포함해야 합니다.

### 3.1 공통 헤더 (Common Headers)
| 헤더명 | 설명 | 생성 로직 / 예시 |
| :--- | :--- | :--- |
| `Host` | API 서버 호스트 | `ac-talk.kakao.com` (Real 환경) |
| `User-Agent` | 클라이언트 식별자 | `KT/{AppVer} An/{OSVer} {Lang}`<br>예: `KT/25.7.2 An/14 ko` |
| `Device-Info` | 기기 하드웨어 정보 | `android/{SDK}; uuid={UUID}; ...` (상세 구조 3.4 참조) |
| `X-VC` | 요청 무결성 검증 토큰 | `SHA512` 해시값의 앞 16자리 (상세 로직 3.5 참조) |
| `A` | 앱 버전 정보 | `android/{AppVer}/{Lang}` |
| `C` | 요청 고유 ID | `UUID` (Request Scope) |
| `Content-Type` | 본문 포맷 | `application/x-www-form-urlencoded; charset=UTF-8` |

### 3.2 단계별 API 규격

#### 3.2.1 로그인 (Step 1)
*   **Endpoint**: `POST https://ac-talk.kakao.com/android/account/login.json`
*   **Content-Type**: `application/x-www-form-urlencoded`
*   **Parameters**:
    *   `email`: 사용자 이메일 계정
    *   `password`: 사용자 비밀번호
    *   `device_uuid`: 기기 고유 식별자 (32 hex chars)
    *   `device_name`: 기기 모델명 (예: `SM-S918N`)
    *   `auto_login`: `true` / `false`
*   **응답 (Response)**:
    *   성공 (기기 등록됨): `{"status": 0, ...}`
    *   성공 (기기 미등록): `{"status": -100, ...}` (이후 Passcode 요청 필요)

#### 3.2.2 인증번호 요청 (Step 2)
*   **Endpoint**: `POST https://ac-talk.kakao.com/android/account/request_passcode.json`
*   **특이사항**: `X-VC` 헤더 생성 시 **전화번호**를 키로 사용해야 함.
*   **Parameters** (추정 - `PhoneNumberParams` 객체 매핑):
    *   `country_code`: 국가 코드 (예: `82`)
    *   `country_iso`: 국가 ISO 코드 (예: `kr`)
    *   `phone_number`: 전화번호 (포맷 주의: `01034838835` 또는 E.164)
    *   `voice_call_language`: (선택) ARS 언어 코드 (예: `ko`)
    *   `codes`: (선택) 추가 인증 정보 리스트 (Push Token 등 가능성 있음)

## 4. 핵심 로직 상세 분석

### 3.4 `Device-Info` 헤더 구조
Java 클래스 `p581JK.C13551c` (`HeaderInterceptor`)에서 생성됩니다.
```text
android/{sdk_int}; uuid={device_uuid}; ssaid={android_id}; model={model_name}; screen_resolution={width}x{height}; sim={iso}/{mccmnc}/{operator_name}; onestore={bool}
```
*   `uuid`: 앱 설치 시 생성되는 고유 32자리 Hex String.
*   `ssaid`: Android ID (Settings.Secure.ANDROID_ID).
*   `sim`: USIM 정보. (유심이 없는 경우 포맷 확인 필요)

### 3.5 `X-VC` 해시 생성 알고리즘 (Integrity Check)
Java 클래스 `p581JK.C13555g` (`XVCHeader`)에서 생성됩니다.

**공통 포맷:**
```text
BARD|{User-Agent}|DANTE|{AccountKey}|SIAN
```
위 문자열을 UTF-8로 인코딩 후 **SHA-512** 해싱하고, Hex String의 **앞 16자리**를 사용합니다.

**AccountKey 결정 규칙:**
1.  **로그인 (`login.json`)**: `email` 값을 사용.
2.  **인증번호 요청 (`request_passcode.json`)**: `phone_number` 값을 사용.
    *   주의: 소스 코드(`p416Gd.C9307c`)에서 `m11141a(phoneNumber)`를 호출하여 직접 헤더를 주입함.

## 5. 네이티브 라이브러리 분석 (Ghidra Findings)

### 4.1 `libtalkand_aes_v11.3.0.so`
이 라이브러리는 카카오톡의 독자적인 암호화 로직을 담당합니다.

*   **주요 함수**: `Java_com_kakao_talk_aes_TalkHello_encrypt`
*   **알고리즘**: AES-256-CBC (PKCS#7 Padding)
*   **정적 키 (Static Key) 추출**:
    *   **Key**: `36 b4 17 d3 2a dd 44 ed a9 5b c6 47 c0 39 ea 22 3a 0e 4b 20 2b 54 15 43 24 34 5a 1a 51 09 40 47` (Little Endian)
    *   **IV**: `c5 a0 6c b4 0a aa e4 9a 57 3c 2f df ab 70 64 28`
*   **용도**: 초기 핸드쉐이크나 민감한 파라미터(예: 전화번호) 암호화에 사용될 가능성이 높음. `request_passcode` 실패 시 파라미터 암호화 시도에 활용 가능.

### 4.2 `libNSaferJNI.so`
NSHC의 보안 솔루션으로 확인되었습니다.

*   **특징**: 외부에서 키를 주입받는 범용 암호화 함수(`N_1Encrypt` 등) 제공.
*   **결론**: 기기 등록 초기 단계보다는 앱 실행 중 무결성 검증이나 데이터 보호에 사용될 것으로 판단됨.

## 6. 트러블슈팅 및 결론

### 현상
Python 스크립트를 통한 `request_passcode` 시도 시, `200 OK` 응답 안에 `{"status": -500}` (Internal Server Error)이 지속적으로 반환됨.

### 분석된 원인
1.  **X-VC 불일치**: 전화번호 포맷(`+82` vs `010`)에 따라 해시값이 달라져 서버 검증 실패 가능성.
2.  **보안 토큰 누락**: `Device-Info`의 `uuid`나 `ssaid`가 서버에 등록된 유효한 패턴이 아니거나, 네이티브 단에서 생성된 추가적인 암호화 토큰(Native Hooking 필요)이 파라미터에 포함되어야 함.
3.  **파라미터 포맷**: JSON 전송 시 `415 Unsupported Media Type` 오류 → `Form-UrlEncoded`가 정답.

## 7. 정적 분석의 한계와 동적 분석의 전환 필요성

### 7.1 정적 분석의 기술적 한계
1.  **난독화로 인한 필드 매핑 불확실성**: JADX로 분석한 `PhoneNumberParams` 클래스의 필드명(`a`, `b`, `c`)이 실제 네트워크 전송 시 어떤 Key(`phoneNumber` vs `phone_number` 등)로 직렬화되는지, `@SerializedName` 어노테이션이 소실된 경우 100% 확신할 수 없습니다. 이는 현재 `-400`/`-500` 오류의 주요 원인입니다.
2.  **동적 생성 데이터 추적 불가**: `runtime`에 생성되는 값(예: `C` 헤더의 UUID, `codes` 리스트의 내용물)이나, 네이티브 단에서 동적으로 계산되는 무결성 검증 값은 정적 코드만으로는 완벽히 재현해내기 어렵습니다.
3.  **서버 측 검증 로직의 불투명성**: 클라이언트 코드가 완벽하더라도, 서버가 `Device-Info`의 특정 조합이나 IP 대역 등을 거부하는 경우, 이는 클라이언트 코드 분석만으로는 원인을 파악할 수 없습니다.

### 7.2 동적 분석(Dynamic Analysis) 도입의 필요성
정적 분석이 "설계도"를 보는 것이라면, 동적 분석은 "실제로 작동하는 기계"를 관찰하는 것입니다.
1.  **정답지(Ground Truth) 확보**: 실제 디바이스에서 카카오톡이 서버로 보내는 패킷을 캡처(Packet Capture)하면, 우리가 추측하고 있는 `Header`와 `Payload`의 정확한 형태를 즉시 알 수 있습니다.
2.  **Hooking을 통한 데이터 탈취**: `Frida`를 사용하여 암호화 직전의 평문(Plaintext)이나, `X-VC` 생성 함수의 입력값을 가로채면, 복잡한 역공학 없이도 알고리즘의 동작 방식을 파악할 수 있습니다.
3.  **네이티브 블랙박스 테스트**: `libtalkand_aes.so`의 내부 로직을 완벽히 이해하지 못해도, 입출력 값을 후킹하여 Python 스크립트에서 재현(Replay)하거나 `ctypes`로 호출할 수 있습니다.

## 8. 동적 분석 시도 및 결과 (Dynamic Analysis Log)

### 8.1 분석 환경 및 도구
*   **Environment**: LDPlayer 9 (Android 9, x86_64 Architecture)
*   **Target App**: KakaoTalk (ARM Architecture, ran via libhoudini translation)
*   **Tools**: Frida 17.5.2, TCPDump, Python Scripts (V1~V6)

### 8.2 Frida Hooking 시행착오
Frida를 이용하여 `request_passcode` 요청 생성 과정을 실시간으로 분석하려 했으나, 다음과 같은 기술적 문제에 직면했습니다.

1.  **Java Realm 접근 실패 (`ReferenceError: 'Java' is not defined`)**:
    *   **원인**: LDPlayer(x86_64) 위에서 실행되는 카카오톡(ARM)은 `libhoudini` 변환 레이어를 통해 구동됩니다. x86_64용 `frida-server`는 프로세스에 Attach는 성공하지만, ARM 샌드박스 내부의 JVM(Java Virtual Machine) 문맥에 진입하지 못했습니다.
    *   **시도**: ARM64용 `frida-server`로 교체하여 실행을 시도했으나, LDPlayer의 호스트 OS가 x86_64인 관계로 실행 즉시 `Aborted` 되었습니다.

2.  **Native Hooking 한계**:
    *   Java Hooking 실패 후, `libtalkand_aes.so` 및 `libc.so` (send/recv) 후킹을 시도했습니다.
    *   **결과**: 프로세스 Attach 및 스크립트 로드는 성공했으나, `SSL_write`나 `send` 함수에서 유의미한 패킷 로그가 포착되지 않았습니다. 이는 앱이 시스템 기본 라이브러리가 아닌 자체 정적 링크된 라이브러리(BoringSSL 등)를 사용하거나, 심볼이 Stripped 되어있기 때문으로 추정됩니다.

### 8.3 Brute-Force 테스트 결과
정적 분석 데이터를 기반으로 `register_device_brute_force.py`를 작성하여 84가지 파라미터 조합(전화번호 포맷, snake_case/camelCase 등)을 테스트했습니다.

*   **결과**: 모든 조합에 대해 **실패**. (Response Code `200`이지만 내부 `status: -500` 또는 `415` 오류)
*   **결론**: 단순한 파라미터 매칭(Plaintext)으로는 통신이 불가능하며, `libtalkand_aes.so`를 통한 **데이터 암호화(Encrypted Payload)** 가 필수적임이 확인되었습니다.

## 9. 향후 개발 가이드 및 권장 환경

### 9.1 권장 분석 환경 (Recommended Setup)
LDPlayer9(x86) 환경에서의 호환성 문제를 해결하기 위해 다음 환경으로의 전환을 강력히 권장합니다.
1.  **Nox Player (Android 7/9)**: Frida 호환성이 매우 우수하며, x86/ARM 변환 이슈가 적습니다.
2.  **실물 안드로이드 기기 (Rooted)**: `HTTP Canary` 등의 앱을 사용하여 HTTPS 패킷을 복호화된 상태로 가장 쉽게 캡처할 수 있습니다. (SSL Pinning Bypass 필요)

### 9.2 구체적 실행 계획 (Action Plan)
1.  **패킷 캡처 (최우선 과제)**:
    *   권장 환경에서 `request_passcode` 성공 시의 **HTTP Body**와 **Header(X-VC)** 를 캡처합니다.
    *   이 "정답지"를 통해 암호화된 필드(예: `phone_number`가 평문인지 암호문인지)를 확인합니다.
2.  **Native Function 호출**:
    *   Python `ctypes` 또는 `Unidbg`를 사용하여 PC에서 `libtalkand_aes.so`의 `encrypt` 함수를 직접 호출, 캡처된 패킷과 동일한 암호문을 생성할 수 있는지 검증합니다.
3.  **최종 구현**:
    *   검증된 암호화 로직을 Python `register_device.py`에 이식하여 기기 등록 자동화를 완성합니다.
