# 1. 카카오톡 프로토콜 분석 및 웹 클라이언트 구현 전략 보고서

## 1. 개요
본 보고서는 `KakaoWebTalk` 프로젝트의 핵심인 "로그인 프로토콜 역공학" 과정에서 획득한 데이터와 실험 결과를 정리하고, 이를 바탕으로 확정된 최종 구현 전략을 기술한다.
초기 PC 클라이언트(`KakaoTalk.exe`)의 메모리 덤프를 통해 인증 데이터를 획득했으나, PC 프로토콜의 복잡성과 폐쇄성으로 인해 **모바일(Android) API 위장 전략**으로 선회하였다.

## 2. 데이터 획득: 메모리 스캔 (Frida)
### 2.1 스캔 기법
Themida로 보호된 PC 클라이언트의 암호화 로직을 우회하기 위해, 네트워크 전송 직전(`send`)의 힙 메모리를 스캔하는 `hook_scan_v2.js`를 개발/사용함.

### 2.2 획득 데이터 (Key Artifacts)
메모리 덤프에서 `x-www-form-urlencoded` 형식의 로그인 페이로드 발견:
```text
email=theman****%40gmail.com
&password=******** // 실제 PW 평문
&device_uuid=supnx3Mu0HpG9brcqZukaAaPxkbBRuSe7WkG1lYzDDyaawfIrMjtA5dlI0Loeb+dBm/9CJmmCzDOqs4fdiIog==
&os_version=10.0
&client_version=3.4.0.0
```
*   **device_uuid**: PC 버전에 등록된 기기 고유값(Base64 Encoded). 서버가 "인증된 PC"임을 식별하는 핵심 키.

## 3. 프로토콜 분석 및 검증 (Trial & Error)

### 3.1 실험 1: PC 프로토콜 흉내내기 (실패)
*   **시도**: 획득한 `device_uuid`와 페이로드를 사용하여 PC 인증 서버(`talk-pilsner.kakao.com`)에 HTTP/1.1 POST 요청 전송.
*   **결과**: `404 Not Found`.
*   **원인**: PC 버전은 표준 HTTP가 아닌 **LOCO 바이너리 프로토콜**을 사용함. 메모리에서 본 텍스트는 내부 구조체일 뿐, 실제 전송 시에는 BSON 등의 바이너리로 변환/암호화되어 전송됨. 이를 모방하려면 바이너리 패킷 전체를 역공학해야 하므로 비효율적임.

### 3.2 실험 2: 모바일 API로 PC 데이터 전송 (부분 실패)
*   **시도**: 안드로이드 인증 서버(`katalk.kakao.com`)에 PC 데이터를 전송.
*   **결과**:
    *   초기: `status: -999` (앱 업데이트 필요) -> 버전 정보가 너무 낮아 거절됨.
    *   버전 수정 후: `status: -500` (서버 내부 오류/파라미터 거절).
*   **원인**: 안드로이드 서버는 PC용 `device_uuid` 포맷이나 `User-Agent`를 허용하지 않음. 즉, "PC 인증 정보"와 "모바일 API"는 호환되지 않음.

## 4. 최종 전략: "안드로이드 앱 위장 (Hybrid Device Spoofing)"

### 4.1 전략 개념
복잡한 PC 프로토콜을 버리고, 분석이 용이하고 표준 HTTP를 사용하는 **안드로이드 API**를 사용한다. PC에서 추출한 정보 중 `이메일`, `비밀번호`는 그대로 사용하되, 기기 식별 정보는 **새로운 안드로이드 기기인 척** 생성하여 보낸다.

### 4.2 상세 구현 로직
1.  **클라이언트 위장**:
    *   `User-Agent`: `KakaoTalk/10.7.3` (최신 안드로이드 버전)
    *   `Header['A']`: `android/10.7.3/ko` (필수 내부 헤더)
2.  **기기 식별자 생성**:
    *   `device_uuid`: 랜덤한 Android ID(SHA1)를 생성하여 전송. (PC UUID 재사용 안 함)
3.  **로그인 프로세스 (웹 클라이언트)**:
    1.  사용자가 웹에 접속하여 카카오 계정(이메일/비밀번호) 입력.
    2.  서버(`katalk.kakao.com`)에 로그인 요청.
    3.  서버 응답: `status: -100` (기기 인증 필요).
    4.  사용자 폰으로 인증번호 발송 요청 API 호출.
    5.  사용자가 웹에 인증번호 입력 -> 기기 등록 완료.
    6.  최종 토큰 발급 및 로그인 성공.

## 5. 결론 및 향후 계획
*   **기술적 난관 돌파**: Themida와 바이너리 프로토콜의 벽을 **"플랫폼 우회(PC -> Android)"** 전략으로 완벽하게 극복함.
*   **Next Step**:
    *   `tests/login_mobile.py`를 파이썬 웹 프레임워크(Flask) 기반의 `KakaoWebTalk` 백엔드로 이식.
    *   기기 등록(Device Register) 프로세스 구현.

# 2. 분석 보고서: 카카오톡 Wear OS APK (v25.7.0)

## 개요
분석된 APK(`com.kakao.talk` Wear OS 버전 25.7.0)는 **컴패니언 애플리케이션(Companion App)**입니다. 이 앱은 자체적으로 기본 인증(로그인)을 수행하지 않으며, 대신 연결된 안드로이드 폰으로부터 **Wear OS DataLayer**를 통해 인증 파라미터(토큰 및 UUID)를 전달받습니다.

## 주요 분석 결과

### 1. 인증 데이터 흐름
- **클래스**: `com.kakao.talk.app.DataLayerListenerService`
- **메커니즘**: Google Play 서비스의 DataLayer를 통해 `AuthItem` 객체를 수신함.
- **데이터 구조 (`AuthItem`)**:
    - `id`: 사용자 ID (long)
    - `token`: 인증 토큰 (string)
    - `uuid`: 기기/설치 UUID (string)
- **결론**: `X-VC` 헤더를 생성하는 구체적인 로직은 이 APK에 존재하지 않습니다. 해당 로직은 인증 데이터가 시계로 동기화되기 전, 폰 측 앱에서 처리되는 것으로 보입니다.

### 2. 네트워크 인터셉터 (헤더)
이 앱은 OkHttp를 사용하며 `p366yb` 패키지에 여러 인터셉터가 포함되어 있습니다:
- **`C6281a` (BreweryInterceptor)**:
    - 추가 헤더: `Authorization: <token>-<uuid>`
    - 추가 헤더: `a: android/<version>/<lang>`
    - 대상: 주로 내부 전용 또는 "Brewery" 엔드포인트로 추정됨.
- **`C6284d` (RequestHeaderInterceptor)**:
    - 추가 헤더: `Authorization: <token>`
    - 추가 헤더: `duuid: <uuid>`
    - 설정: `Content-Type: application/json`
- **`C6283c` (NodeInterceptor)**:
    - 추가 헤더: `resolution`, `density_dpi`, `density`.

### 3. 미포함 요소
- **`X-VC` 생성 로직 부재**: "X-VC", "XVC", 또는 카카오 솔트(`73AC0778...`)를 이용한 해싱 로직을 광범위하게 검색하고 인터셉터를 수동으로 검사했으나 결과가 없었습니다.
- **`libtalkand_aes.so` 부재**: 일반 안드로이드 앱에서 암호화를 담당하는 네이티브 라이브러리가 포함되어 있지 않습니다.
- **`login.json` 부재**: 기본 로그인을 위한 엔드포인트가 이 APK에는 정의되어 있지 않습니다.

### 4. 암호화 유틸리티
- **`p245qb.C4210n.m8766a`**: 하드코딩된 RSA 개인키가 포함되어 있으며, 이는 **채팅 로그 응답(Chat Log Response)**을 복호화하는 데 사용됩니다. (E2EE 또는 보안 저장소 용도로 추정)
- **`p202nb.C3655d`**: 애플리케이션의 서명 해시(Key Hash)를 추출하기 위한 표준 SHA-1 해싱 기능.

## 다음 단계
`X-VC` 생성 로직을 확실하게 찾아내고 리버싱하기 위해서는 **표준 스마트폰용 APK**(`com.kakao.talk`)가 필요합니다. Wear OS 버전은 메인 앱에서 제공하는 토큰 기반의 단순화된 세션을 사용하기 때문입니다.

# 3. 카카오톡 안드로이드 로그인 프로토콜 검증 보고서

## 목적
Python 스크립트를 사용하여 카카오톡 안드로이드 로그인 API 엔드포인트, 필수 헤더 요구사항 및 인증 흐름을 검증합니다.

## 분석 결과

### 1. API 엔드포인트
- **식별된 호스트**: `katalk.kakao.com` 및 `ac-talk.kakao.com`
- **주요 엔드포인트**: `/android/account/login.json`
- **통신 방식**: `POST`
- **Content-Type**: `application/x-www-form-urlencoded; charset=UTF-8`

### 2. 필수 헤더 (Required Headers)
서버는 `Android` 클라이언트 서명을 기반으로 엄격한 헤더 유효성 검사를 수행합니다.
- **X-VC (Verification Code)**:
  - 생성 공식: `SHA512("BARD|{device_info}|DANTE|{email}|SIAN").substring(0, 16)`
  - 주의: `{device_info}`는 `User-Agent` 문자열과 정확히 일치해야 합니다.
- **User-Agent**:
  - 형식: `KT/{version} An/{os_ver} {lang}`
  - 예시: `KT/25.7.2 An/14 ko`
  - **참고**: 일반적인 `KakaoTalk/...` 형태의 User-Agent는 이 API에서 "앱 업데이트 필요" 오류를 발생시킵니다.
- **Header "A"** (내부 버전 검사):
  - 형식: `android/{version}/{lang}`
  - 예시: `android/25.7.2/ko`
- **Header "C"** (요청 ID):
  - 형식: `UUID` (무작위 생성된 UUID v4 허용됨).
- **Device-Info**:
  - 형식: `android/{sdk_int}; uuid={uuid}; ssaid={ssaid}; model={model}; screen_resolution={res}; sim={sim}; onestore=false`
  - 예시: `android/34; uuid=...; ssaid=...; ...`

### 3. 비밀번호 전송 방식
- **암호화 여부**: 정적 분석 결과, 일부 로직에서 AES 난독화가 확인되었으나, 실제 `/android/account/login.json` 엔드포인트로 전송될 때는 **평문(Plaintext)**으로 JSON Body에 포함되어 전송됩니다. 해당 API는 HTTPS를 통해 보안이 유지됩니다.
- **Body 파라미터**:
  ```json
  {
      "email": "user@example.com",
      "password": "plaintext_password",
      "device_uuid": "...",
      "device_name": "...",
      "auto_login": "false"
  }
  ```

### 4. 검증 결과
- **스크립트**: `tests/login_mobile.py`
- **결과**:
  - **Status 30**: 비밀번호가 틀렸을 때 반환됨 (요청 규격 정상 확인).
  - **Status -100**: 올바른 계정 정보로 로그인 시도 시 반환됨. 이는 **"기기 등록 필요(Device Not Registered)"** 상태를 의미하며, 서버가 클라이언트 요청을 정상적으로 수락하고 계정 검증까지 완료했음을 확인해줍니다.
  - **ServerTime**: 응답에 `serverTime`이 포함되어 돌아오며, 이는 정상적인 API 응답 구조입니다.

## 향후 계획
- **기기 등록 프로세스 구현**: Status -100 응답 시 수행해야 하는 2단계 인증(기기 등록) 로직을 구현합니다.
- **OAuth 토큰 획득**: 기기 등록이 완료된 후 발급되는 OAuth 토큰을 획득하여 세션을 유지합니다.

# 4. Mobile Login Debugging Log (-500 Error Analysis)

## Objective
Identify the cause of the `status: -500` (Internal Server Error / Unknown Error) response from `https://katalk.kakao.com/android/account/login.json` when emulating an Android client.

## Baseline
- **Target**: `https://katalk.kakao.com/android/account/login.json`
- **User-Agent**: `KakaoTalk/10.6.5`
- **Headers**: `A: android/10.6.5/ko`
- **Payload**: `email`, `password`, `device_uuid` (Android-style hash), `os_version`, `client_version`, `model`, `country_iso`, etc.
- **Current Result**: `{"status": -500}`

## Debugging Session

### Hypothesis 1: `device_id` vs `device_uuid` Mismatch
**Theory**: The `device_uuid` field in LOCO/Kakao protocol is typically a SHA1 hash of the `device_id` (or `android_id`). The server might require the *raw* `device_id` parameter to be present and match the hash provided in `device_uuid`.
**Action**: Modify script to send both `device_id` (raw hex) and `device_uuid` (encoded hash).

### Hypothesis 2: Payload Encoding (JSON vs Form)
**Theory**: While `Content-Type` is set to `x-www-form-urlencoded`, requests library might be encoding characters in a way the legacy server dislikes.
**Action**: Ensure proper URL encoding, or try standard `data` dict which `requests` handles effectively. (Already doing this, but might triple check). Alternatively, some endpoints accept JSON body.

### Hypothesis 3: Missing `bg_token` (Push Token)
**Theory**: Login might fail if the push token (`push_token` or `bg_token`) is "dummy". It might check format.
**Action**: Use a realistic-looking FCM token format.
