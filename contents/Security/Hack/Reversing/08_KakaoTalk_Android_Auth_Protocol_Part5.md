## 0. 정적 분석의 병목
4편에서 네이티브 라이브러리(`libtalkand_aes.so`)로부터  
AES-256-CBC **Key/IV**를 식별하고, `uvc3` 토큰의 암호화·복호화 구조까지 확인했다.

그러나 곧바로 한계에 부딪혔다.

- `uvc3` 내부 필드 수가 많고
- 각 필드의 **자료형(Integer / Float / String)**과 **단위**가 제각각이며
- 일부 값은 **단말 모델·환경에 강하게 종속**

이 모든 것을 사람이 수작업으로 역추적하기에는  
시간 대비 효율이 급격히 떨어지는 구간이었다.

---

## 1. 자율형 에이전트 기반 분석 설계
이 문제를 해결하기 위해,  
분석 작업을 **자율형 AI 에이전트**로 분산 처리하는 방식을 선택했다.

### 1.1 에이전트 구성
- **메인 오케스트레이터**
  - 전체 분석 계획 수립
  - 태스크 분해 및 결과 취합
- **Native Hunter**
  - Ghidra 분석 결과를 기준으로
    네이티브 심볼, 상수, 필드 생성 로직 추적
- **The Chronicler**
  - 분석 결과를 즉시 코드로 전환
  - Python 구현 시 필요한 타입·포맷 명세화

이 구조는 내부적으로  
:contentReference[oaicite:0]{index=0}라는  
자율형 에이전트를 중심으로 동작하도록 구성했다.

핵심 목표는 단순했다.

> **uvc3 페이로드를 서버가 기대하는 형태로 최대한 정확히 재현한다.**

---

## 2. uvc3 페이로드 상세 복원 결과
병렬 분석을 통해, 수동 분석으로는 놓치기 쉬웠던  
세부 규칙들이 명확해졌다.

### 2.1 주요 필드 규칙
- **`batteryPct`**
  - `1.0` 같은 부동소수점이 아닌
  - **정수형(Integer) `100`**을 기대
- **`totalMemory`**
  - 에뮬레이터의 일반적인 값이 아닌
  - 실제 단말 기준 메모리 값 사용
  - 예: Galaxy S23 계열 → `11162484736`
- **`tpn_eq_sim`**
  - `0`일 경우 서버 검증 실패
  - **반드시 `1`로 설정되어야 정상 처리**

이 외에도,
- SIM 배열 구조
- 문자열 길이 제한
- 특정 필드의 존재 여부

등이 서버 측 검증 로직에 직접적인 영향을 주는 것으로 확인되었다.

## 3. 정적 분석 결과의 집대성
분석 결과를 모두 반영하여,  
다음 요소를 포함한 최종 스크립트를 구성했다.

- APK에서 추출한 **`stamp-cert-sha256`**
- 네이티브에서 확보한 **AES-256 Key / IV**
- 에이전트가 복원한 **정밀 uvc3 페이로드**
- Form-Encoded 요청 구조 및 헤더 세트

이 결과물은  
`register_device_v24.py`로 정리되었다.

정적 분석 관점에서 가능한 모든 요소를 반영한,  
사실상 **완성형 구현**에 가까웠다.

---

## 4. 결과와 해석
스크립트를 실행한 결과는 다음과 같았다.

- HTTP 응답: `200 OK`
- 내부 상태 코드: `status: -500`

즉,

- 암호화 로직: 재현 성공
- Key / IV: 정확
- 페이로드 구조: 서버 기대치 충족
- **데이터의 “출처”**: 검증 실패

서버는 단순히 값의 형태만 보는 것이 아니라,  
**실제 단말에서 생성된 데이터인지 여부**를  
다층적으로 판단하고 있었다.

---

## 5. 정적 분석의 종료 지점
이 시점에서 명확해진 결론은 다음과 같다.

- 알고리즘과 키를 알아도 충분하지 않다
- 데이터가 “어디에서 생성되었는지”가 핵심이다
- 정적 분석만으로는 서버의 최종 검증을 통과할 수 없다

즉,  
**정적 분석(Static Analysis)**의 유효 범위는 여기까지다.

---

## 정리
5편에서는 다음을 확인했다.

- uvc3 페이로드는 단순 JSON이 아닌, 엄격한 규칙 집합
- 일부 필드는 값 자체보다 **현실성**이 중요
- 자율형 에이전트 기반 분석은 생산성을 크게 향상시킴
- 그럼에도 불구하고, 정적 분석만으로는 최종 인증 불가
