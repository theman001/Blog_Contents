## 0. 설계도는 거짓말을 하지 않는다. 하지만…
이 시리즈를 통해 우리는 카카오톡 안드로이드 인증 프로토콜의 구조를 단계적으로 해체해 왔다.

- 자바 레이어에서 인증 로직과 파라미터 구조를 복원했고  
- 네이티브 라이브러리에서 AES-256 암호화 로직과 Key·IV를 추출했으며  
- `uvc3` 페이로드의 내부 구조까지 재현했다  

기술적으로 보자면, **클라이언트가 무엇을 어떻게 생성하는지**에 대한 설계도는 거의 완벽하게 확보한 셈이다.

그럼에도 불구하고,  
우리가 만든 요청은 마지막 순간마다 서버로부터 동일한 응답을 받았다.

- HTTP: `200 OK`  
- 내부 상태 코드: **`-500 (Internal Server Error)`**

이 지점에서 중요한 질문이 남았다.

> “우리는 무엇을 아직 재현하지 못한 것인가?”

---

## 1. 정적 분석이 마주한 ‘값’의 문제
분석이 깊어질수록 분명해진 사실은 하나였다.

**문제는 알고리즘이 아니라, 데이터였다.**

### 1.1 무결성 검증의 실제 기준
- **`apkChecksum`**
  - 서버는 단순히 해시 형식만 확인하지 않는다
  - 실제 공식 마켓에 배포된 APK의 서명 해시와 대조한다
- **기기 식별 토큰(e 등)**
  - 임의로 생성한 값은 즉시 배제된다
  - 특정 단말 환경에서 생성·등록된 이력이 있는 값만 유효하다

### 1.2 데이터 타입과 단위의 엄격함
- 배터리 잔량
  - `1.0` → 실패
  - `100` → 정상
- 메모리, SIM 정보, 하드웨어 식별 값
  - 값의 범위뿐 아니라 **현실성과 일관성**이 함께 검증된다

정적 분석은  
**“어떻게 생성되는가(How)”**는 알려주지만,  
**“서버가 지금 이 순간 기대하는 값이 무엇인가(What)”**까지는 보장하지 않는다.

---

## 2. 정적 분석의 한계 정리
여기까지의 결과를 요약하면 다음과 같다.

- 암호화 알고리즘: 재현 가능
- Key / IV: 추출 가능
- 페이로드 구조: 재현 가능
- **실제 서비스 환경에서 생성된 값**: 재현 불가

즉, 서버는 단순히 요청의 형태를 검사하는 것이 아니라  
**요청이 생성된 맥락과 출처**를 함께 판단하고 있었다.

이 지점이 바로 정적 분석의 종료선이다.

---

## 3. 방향 전환: 동적 분석(Dynamic Analysis)
이제 접근 방식을 바꿀 수밖에 없었다.

가짜 데이터를 “만드는” 것이 아니라,  
**진짜 데이터가 생성되는 순간을 관찰하는 것**이다.

이를 가능하게 하는 도구가 **Frida**다.

Frida는 실행 중인 앱 프로세스에 개입하여,

- 함수 호출 시점의 인자
- 암호화 직전의 평문 데이터
- 런타임에서만 생성되는 토큰

을 그대로 확인할 수 있게 해준다.

---

## 4. 최종 전략 개요
정적 분석 이후 설정한 최종 전략은 다음과 같다.

1. **대상 지점**
   - `TalkHello.encrypt()` 등 네이티브 암호화 함수 호출 직전
2. **목표**
   - 암호화되기 전 상태의 **실제 uvc3 JSON** 확보
3. **활용**
   - 확보한 실제 값(`apkChecksum`, 기기 토큰 등)을
     기존 `register_device_v24.py` 로직에 주입
4. **검증**
   - 서버 응답 변화 여부 확인

이 단계부터는 더 이상 추측이 아니라,  
**현장에서 생성되는 정답 데이터**를 기준으로 분석이 진행된다.

---

## 5. 시리즈를 마치며
이 시리즈는 단순한 취약점 탐색이나 기능 우회 기록이 아니다.

- 자바와 JNI 구조
- 네이티브 바이너리 분석
- 암호화 알고리즘
- 자동화와 AI 기반 보조 분석

을 종합적으로 활용해,  
현대 모바일 애플리케이션의 인증 구조가  
어디까지 정적 분석으로 이해 가능하고,  
어디서부터 동적 분석이 필수적인지를 보여주는 기록이다.

정적 분석은 실패가 아니라 **기초 체력**이다.  
우리가 확보한 암호화 로직과 Key·IV는  
이후 동적 분석 단계에서 패킷을 해석하고 검증하는 데
가장 강력한 도구가 된다.
