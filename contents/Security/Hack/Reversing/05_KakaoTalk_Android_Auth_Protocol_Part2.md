## 0. 설계도를 입수하다
1편에서 확인한 `-500` 오류는 하나의 분명한 사실을 보여주었다.

> 서버는 “요청을 해석할 수 없음”이 아니라  
> "**클라이언트가 규격을 충족하지 않는다**"고 판단하고 있다.

이제 더 이상 패킷 조합만으로는 답이 나오지 않는다.  
서버가 기대하는 **정확한 요청 규격**을 알아내기 위해,  
카카오톡 안드로이드 APK 자체를 분석하기로 했다.

본 편에서는 **JADX를 이용한 자바 레이어 정적 분석** 결과를 정리한다.

---

## 1. X-VC 헤더 생성 로직 분석
가장 먼저 분석 대상이 된 것은 모든 요청에 포함되던 **X-VC 헤더**다.  
이 값이 잘못되면 서버는 정상 응답을 반환하지 않는다.

### 1.1 X-VC 생성 알고리즘
관련 클래스를 추적한 결과,  
X-VC는 다음과 같은 문자열을 기반으로 생성된다.

```text
BARD|{User-Agent}|DANTE|{AccountKey}|SIAN
```
위 문자열을 **SHA-512**로 해싱한 뒤,  
결과 Hex 문자열의 **앞 16자리**를 X-VC 값으로 사용한다.

### 1.2 AccountKey 전환 규칙
여기서 중요한 부분은 `{AccountKey}`의 의미다.

- **로그인 요청 (`login.json`)**
  - AccountKey = 사용자 **Email**
- **인증번호 요청 (`request_passcode.json`)**
  - AccountKey = 사용자 **Phone Number**

즉, 인증 단계에 따라  
X-VC 생성에 사용되는 입력값이 **의도적으로 변경**된다.

1편에서 로그인 성공 후 인증 요청이 실패했던 이유 중 하나는  
이 **키 전환 규칙을 반영하지 못했기 때문**이다.

## 2. PhoneNumberParams 구조 분석
다음 분석 대상은  
`request_passcode` 요청 시 사용되는 파라미터 객체인  
**PhoneNumberParams** 클래스다.

### 2.1 필드 매핑 결과
난독화된 필드를 역추적한 결과는 다음과 같다.

| 난독화 필드명 | 의미 (추정) | 예시 |
|---|---|---|
| `f160206a` | countryCode | `"82"` |
| `f160207b` | countryIso | `"kr"` |
| `f160208c` | phoneNumber | `"010XXXXXXXX"` |
| `f160210e` | codes | `[]` |

이 객체는 Retrofit을 통해  
Form-Encoded 또는 JSON 형태로 직렬화되어 전송된다.

---

## 3. 직렬화 방식의 불확실성
여기서 중요한 문제가 하나 발생한다.

> 서버는 `phoneNumber`를 기대하는가,  
> 아니면 `phone_number`를 기대하는가?

Retrofit은 다음 조건에 따라 직렬화 결과가 달라진다.

- `@SerializedName` 어노테이션 존재 여부
- Converter 설정
- 인터페이스 메서드 선언 방식

그러나 **정적 분석만으로는**  
실제 네트워크 전송 시 사용되는 Key 이름을  
100% 확정하기 어렵다.

이로 인해  
다양한 파라미터 조합(camelCase / snake_case)에 대한  
브루트 포스 테스트가 필요해졌다.

---

## 4. 숨겨진 필드: simParams
분석 중 가장 중요한 발견은  
기존 패킷 캡처에서는 보이지 않았던  
**추가 필드의 존재**였다.

### 4.1 유령 필드 `f`
`PhoneNumberParams` 내부에는  
문서화되지 않은 또 하나의 필드(`f`)가 존재하며,  
이 값은 **USIM 정보(simParams) **를 담고 있다.

특징은 다음과 같다.

- 자바 코드에서 직접 생성되지 않음
- **네이티브 메서드 호출 결과**를 통해 값이 주입됨
- 단순 문자열이 아닌 구조화된 데이터

이 필드는 선택 항목이 아니라,  
**실제 단말 환경을 증명하는 필수 정보**로 보인다.

---

## 5. 자바 레이어 분석의 한계
이 시점에서 확인된 사실은 다음과 같다.

- X-VC 생성 규칙은 자바 레이어에서 확인 가능
- 파라미터 구조 역시 자바 코드로 파악 가능
- 그러나 **일부 핵심 값은 자바에서 생성되지 않는다**

특히 다음 질문에는 답을 할 수 없었다.

- simParams의 실제 값은 어떤 로직으로 생성되는가?
- 네이티브 계층에서 추가되는 무결성 정보는 무엇인가?
- 왜 자바 로직을 그대로 구현해도 서버는 요청을 거부하는가?

모든 단서는 하나의 방향을 가리킨다.

> **JNI를 통해 호출되는 네이티브 라이브러리(.so)**

## 정리
2편에서는  
JADX 기반 정적 분석을 통해 다음을 확인했다.

- X-VC 헤더의 정확한 생성 알고리즘
- 인증 단계별 AccountKey 전환 규칙
- PhoneNumberParams의 실제 구조
- 네트워크 패킷에는 보이지 않던 필수 네이티브 필드 존재

하지만 동시에,  
**자바 레이어만으로는 재현할 수 없는 영역**이 분명히 드러났다.
