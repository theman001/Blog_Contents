## 0. 시작하며
어느 순간 의문이 들었다.

> 카카오톡은 안드로이드 환경에서 어떤 방식으로 기기를 인증하고 통신을 보호하고 있을까?”

이 글은 그 질문에서 출발한 기록이다.  
카카오톡 안드로이드 클라이언트의 **인증 및 기기 등록 프로토콜**을 분석하고,  
이를 PC 환경에서 에뮬레이션하려는 과정에서 확인된 기술적 제약과 한계를 정리한다.

본 편(1편)에서는  
정적 분석에 들어가기 전 단계로서,  
**실제 트래픽 관찰과 패킷 분석 과정에서 확인된 현상**을 중심으로 다룬다.
> #1 시리즈 후편으로, #2편 시리즈 작성

---

## 1. 트래픽 관찰과 엔드포인트 식별
가장 먼저 수행한 작업은  
**실제 안드로이드 기기에서 발생하는 네트워크 트래픽 관찰**이다.

HTTPS 프록시를 구성한 뒤  
로그인 및 기기 등록 흐름을 확인한 결과,  
다음과 같은 핵심 엔드포인트를 식별할 수 있었다.

- **로그인**
  - `/android/account/login.json`
- **인증번호 요청**
  - `/android/account/request_passcode.json`
- **기기 등록**
  - `/android/account/register_device.json`

표면적으로 보면,  
로그인 → 인증번호 요청 → 기기 등록  
이라는 비교적 단순한 단계로 구성된 흐름이다.

---

## 2. 로그인 단계 분석 — Status `-100`
Python 환경에서 `requests` 라이브러리를 사용해  
`login.json` 엔드포인트에 직접 요청을 전송했다.

서버 응답은 다음과 같았다.

`{
  "status": -100,
  "serverTime": 1768917869
}`

`status: -100`의 의미는 다음과 같다.

- 아이디 / 비밀번호 검증은 **정상적으로 완료**
- 현재 요청을 보낸 기기는 **미등록 상태**

즉, 서버는 계정 정보 자체는 신뢰하고 있으며,  
기기 등록 절차만 남아 있는 상태임을 명확히 알려준다.

이 결과를 통해  
기본적인 인증 정보 처리 로직은  
PC 환경에서도 재현 가능하다는 점을 확인할 수 있었다.

---

## 3. 인증번호 요청 단계 — `-500` 오류
문제는 다음 단계였다.

기기 등록을 위해  
`request_passcode.json` 엔드포인트로 요청을 전송하자,  
지속적으로 오류가 발생했다.

시도 결과를 정리하면 다음과 같다.

| 시도 방식 | 결과 | 상태 코드 | 분석 |
|---|---|---|---|
| JSON Payload | 실패 | 415 | Unsupported Media Type (JSON 미허용) |
| Form-Data | 실패 | 200 (`status: -500`) | 서버 내부 오류 |
| snake_case 파라미터 | 실패 | 200 (`status: -400`) | Bad Request |

특이한 점은 다음과 같다.

- HTTP 레벨에서는 `200 OK`를 반환
- 응답 본문에서 내부 상태 코드(`-500`, `-400`)로 요청을 거부

이는 단순한 서버 장애나 네트워크 오류가 아니라,  
**의도적인 요청 검증 실패 처리**로 보인다.

---

## 4. 보안 헤더의 존재
요청 본문만으로는 원인을 설명할 수 없었다.

실제 안드로이드 앱에서 전송되는 패킷을 비교 분석한 결과,  
다음과 같은 **보안 관련 헤더**들이 항상 포함되어 있었다.

- **X-VC**
  - 요청 무결성 검증을 위한 해시 기반 값
- **Device-Info**
  - 기기 모델, OS 버전, 해상도, SIM 정보 등을 포함한 문자열
- **A / C 헤더**
  - 앱 버전 정보 및 요청 단위 식별자

이 값들은 임의로 생성된 값이 아니라,  
앱 내부 로직을 통해 **일관된 규칙에 따라 계산**된다.

이 중 하나라도 정확하지 않을 경우,  
서버는 해당 요청을 정상적인 클라이언트 요청으로 인정하지 않고  
내부 상태 코드 `-500` 또는 `-400`으로 처리한다.

---

## 5. 정리 — 패킷 분석의 한계
이 단계에서 다음과 같은 결론에 도달했다.

- 단순한 파라미터 조합이나 포맷 변경만으로는
  `request_passcode` 요청을 통과할 수 없다.
- 서버는 **클라이언트 무결성**을 함께 검증하고 있다.
- 이 무결성 검증 로직은
  네트워크 패킷만으로는 완전히 재현할 수 없다.

즉, **블랙박스 관점의 패킷 분석만으로는 한계가 명확**하다.
