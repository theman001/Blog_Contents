# 2. 바이너리 로직 심층 분석 보고서

## 1. 개요 및 분석 대상 (Target Overview)
- **대상 파일**: `KakaoTalk.exe` (메인 실행 파일), `Vox3.dll` (음성/통화 및 핵심 로직), `domain_actions.dll`.
- **보호 기법 (Protection)**: **Themida / WinLicense** 패킹 감지.
    - **영향**: Ghidra를 이용한 정적 분석 시, 프로그램의 진입점(`entry`)과 난독화된 섹션(`.themida`), `.reloc` 등만 보이며 실제 비즈니스 로직 언패킹 전에는 보이지 않음.
    - **대응책**: 정적 분석만으로는 한계가 명확하며, 실행 중인 프로세스의 **메모리 덤프(Memory Dump)** 또는 **동적 디버깅**이 필수적임.

## 2. 정적 문자열 및 구조 분석 결과 (Analysis Findings)
패킹으로 인해 함수 흐름(Flow)은 볼 수 없으나, 바이너리에 포함된 문자열(String)과 임포트 테이블을 통해 핵심 동작을 추론함.

### 2.1. 암호화 메커니즘 (Encryption & Security)
- **라이브러리 식별**:
    - **CNG (Cryptography Next Generation)**: `bcrypt.dll` 임포트 및 `BCryptGenRandom` 함수 호출 확인. 이는 난수 생성 및 키 관리에 Windows 표준 API를 사용함을 시사.
    - **OpenSSL**: `Vox3.dll` 내부에서 `OpenSSL` 관련 문자열 패턴 식별. 별도의 `libssl.dll` 파일이 없는 것으로 보아, 카카오톡 바이너리 내부에 **정적 링크(Static Linking)** 되어 있음.
    - **알고리즘**: `AES` 문자열이 다수 발견됨. 
- **특이 심볼**:
    - `?decrypt_vox_bson_msg_voiceroom@@YAHPBDHPA_JPAH12122111@Z`
    - 위 심볼(Name Mangling 해제 전)은 `Vox3.dll`이 **BSON(Binary JSON)** 포맷의 메시지를 처리하며, 이를 **복호화(decrypt)** 하는 전용 함수를 가지고 있음을 보여줌. 이는 채팅 또는 보이스룸 시그널링 데이터로 추정됨.
- **키 저장소**:
    - AppData 경로의 `.cng` 파일들은 Windows CNG Key Storage Provider가 관리하는 로컬 키 컨테이너로, 기기 고유 키나 세션 키가 저장될 가능성이 높음.

### 2.2. 통신 및 프로토콜 (Communication)
- **프로토콜**: `LOCO` 프로토콜 관련 명시적 문자열은 패킹됨. 그러나 `Vox3.dll`의 구조상 통신 핵심을 담당하는 것으로 보임.
- **주요 클래스 (Exported Classes)**:
    - `IVoxManager`: 전반적인 음성/세션 매니저.
    - `IVoxCall`: 통화 기능 인터페이스.
    - `IVoxScreenShare`: 화면 공유 기능 인터페이스.
- **네트워크 라이브러리**:
    - `WinHttp` 문자열 다수 발견. 로그인, 프로필 사진 다운로드 등의 RESTful 요청은 `WinHttp` API를 사용하는 것으로 추정됨.

### 2.3. 설정 및 로컬 데이터 (Config & Data)
- **`user_pref.ini`**:
    - 사용자 UI 상태(창 위치, 이모티콘 설정) 및 실험실 기능(`use_lab`) 활성화 여부를 저장. 평문 또는 단순 인코딩된 텍스트.
- **`login_list.dat`**:
    - 로그인한 이메일 계정 정보 저장. 일부 평문(`theman7684@gmail.com`) 노출 확인, 나머지는 파이프(`|`) 구분자로 구조화됨.

## 3. 기술적 제언 및 향후 계획 (Recommendations & Next Steps)

1.  **인증 로직 구현 전략**:
    - 현재 바이너리가 패킹되어 있어 정확한 해싱 알고리즘(`SHA` 등)의 파라미터 확인이 어려움.
    - **우회 전략**: Wireshark를 통한 패킷 캡처로 로그인 시 전송되는 HTTP 헤더와 페이로드를 분석하여, 이를 그대로 모방(Replay/Simulation)하는 방식을 우선 시도해야 함.

2.  **필수 추가 작업**:
    - **메모리 덤프 확보**: 카카오톡 로그인 후 `KakaoTalk.exe` 및 `Vox3.dll`의 메모리 덤프를 생성하여 Themida 패킹을 우회해야 `AES` 키 생성 로직을 정확히 파악 가능.
    - **패킷 캡처**: 로그인 시점의 트래픽을 캡처하여 `Login` API 엔드포인트와 파라미터 구조를 파악해야 함.

# 4. Themida 우회 및 분석 전략 보고서

## 1. 개요
본 보고서는 Themida로 패킹된 `KakaoTalk.exe` 및 `Vox3.dll`을 분석하기 위해, 빌드 난이도가 높은 `TitanHide`를 사용하지 않고 우회할 수 있는 현실적인 대안 기술들을 제시합니다.

## 2. 핵심 전략: "실행 후 메모리 덤프 (Run & Dump)"
Themida 분석의 핵심은 **"코드가 실행되어 메모리에 풀린 상태"**를 확보하는 것입니다. 굳이 디버거를 처음부터 붙여서 싸울 필요는 없습니다.

### 전략 프로세스
1.  **실행(Execute)**: 카카오톡을 정상적으로 실행시킵니다.
2.  **언패킹 대기(Wait)**: 로그인 화면이 뜰 때까지 기다립니다. (이때 이미 메모리 상에는 코드가 풀려 있습니다.)
3.  **은밀한 접근(Stealth Attach/Suspend)**: Themida가 감지하지 못하는 도구로 프로세스에 접근합니다.
4.  **덤프(Dump)**: 메모리 영역을 파일로 저장합니다.
5.  **복구(Fix)**: IAT(Import Address Table)를 복구하여 Ghidra에서 분석 가능하게 만듭니다.

## 3. TitanHide 대안 기술

### 대안 1: ScyllaHide (추천)
TitanHide보다 훨씬 사용하기 쉽고 강력한 플러그인입니다.
*   **작동 방식**: 디버거(x64dbg)가 OS에 요청하는 정보를 중간에서 가로채서(Hooking) 디버거가 없는 것처럼 속입니다.
*   **장점**:
    *   **설치가 쉽습니다**: x64dbg 폴더에 파일만 넣으면 끝납니다. (별도 드라이버 빌드 불필요)
    *   **옵션 선택 가능**: Themida 전용 프로필이 있어 클릭 한 번으로 설정 가능합니다.
*   **실행 방법**:
    1.  `x64dbg` 최신 버전 다운로드.
    2.  `ScyllaHide` 플러그인 설치 (x64dbg 플러그인 폴더에 복사).
    3.  x64dbg 실행 -> Plugins -> ScyllaHide -> Options -> **"Themida/WinLicense"** 프로필 선택 -> OK.
    4.  F3 눌러서 카카오톡 실행.

### 대안 2: Process Suspend & Dump (가장 쉬움)
디버거를 아예 붙이지 않고, 시스템 관리 도구로 메모리만 퍼내는 방법입니다. Themida는 주로 "디버거 부착"을 감지하지, 단순 시스템 도구의 접근까지 모두 막지는 못하는 경우가 많습니다.
*   **도구**: Process Hacker 2 (또는 System Informer)
*   **방법**:
    1.  카카오톡 실행 후 로그인 창 대기.
    2.  Process Hacker를 **관리자 권한**으로 실행.
    3.  `KakaoTalk.exe` 우클릭 -> **Suspend** (프로세스 일시정지).
    4.  다시 우클릭 -> **Create Dump File...** -> **Full Dump** 선택.
    5.  생성된 `.dmp` 파일을 Ghidra에 넣거나, `mimidump` 같은 도구로 변환.
    *   *주의: 이 방법은 덤프는 쉽지만, IAT 복구가 자동으로 되지 않아 Ghidra에서 함수 이름을 보려면 추가 작업(Scylla Import Reconstruction)이 필요할 수 있습니다.*

### 대안 3: VM Hardening (가상머신 탐지 우회)
현재 VM 환경에서 작업 중이시므로, TitanHide가 없더라도 **VM 자체를 리얼 머신처럼 보이게** 만들면 Themida가 "VM에서 분석 중"이라는 사실을 눈치채지 못합니다.
*   **방법**: `.vmx` 파일(VMware 기준) 수정.
    ```
    isolation.tools.getPtrLocation.disable = "TRUE"
    isolation.tools.setPtrLocation.disable = "TRUE"
    isolation.tools.setVersion.disable = "TRUE"
    isolation.tools.getVersion.disable = "TRUE"
    monitor_control.disable_directexec = "TRUE"
    monitor_control.disable_chksimd = "TRUE"
    ... (상세 스크립트는 인터넷에 'VMware Hardening' 검색)
    ```

## 4. 추천 분석 로드맵
TitanHide 빌드에 시간을 쏟기보다는, **대안 1 (ScyllaHide)** 또는 **대안 2 (Process Hacker)**를 먼저 시도하는 것을 강력히 권장합니다.

1.  **우선 순위 1**: **Process Hacker**로 `Suspend` 후 `Full Memory Dump` 시도. (가장 빠름)
2.  **우선 순위 2**: **x64dbg + ScyllaHide** 조합으로 카카오톡 실행 시도.
3.  **최후의 수단**: 위 방법들이 모두 막힐 때만 커널 드라이버(TitanHide) 빌드 재시도.

# 5. ScyllaHide 설치 및 사용 가이드

## 1. 개요 (Description)
ScyllaHide는 사용자 모드(Ring3)에서 작동하는 강력한 안티-안티-디버깅(Anti-Anti-Debug) 라이브러리입니다. 특정 Windows API 함수들을 후킹(Hooking)하여 디버거의 존재를 감지하려는 시도를 차단합니다. 커널 모드 드라이버인 TitanHide와 달리 설치가 간편하며 호환성이 좋습니다.

## 2. 설치 방법 (Installation)

`ScyllaHide`는 디버거의 플러그인 형태로 동작합니다. 현재 분석에 가장 적합한 **x64dbg** 기준으로 설명을 진행합니다.

### x64dbg 설치 경로
*   x64dbg가 설치된 폴더 (예: `C:\x64dbg\release`)

### 파일 복사 (2.5절 참조)
ScyllaHide 배포 파일에서 다음 파일들을 x64dbg 플러그인 폴더로 복사해야 합니다.

**64-bit (KakaoTalk 분석용)**
1.  **원본 위치**: ScyllaHide 폴더
2.  **대상 위치**: `\x64\plugins\` (x64dbg 폴더 내)
3.  **복사할 파일**:
    *   `HookLibraryx64.dll` (핵심 후킹 라이브러리)
    *   `ScyllaHideX64DBGPlugin.dp64` (x64dbg용 플러그인 파일)
    *   `scylla_hide.ini` (설정 파일)

**32-bit (참고용)**
1.  **대상 위치**: `\x32\plugins\`
2.  **복사할 파일**: `HookLibraryx86.dll`, `ScyllaHideX64DBGPlugin.dp32`, `scylla_hide.ini`

> **주의**: `HookLibraryx64.dll` 등의 파일이 플러그인 폴더에 정확히 위치해야 로드가 됩니다.

## 3. Themida 우회 설정 (Configuration)

설치가 완료되면 x64dbg를 실행하고 `Plugins` -> `ScyllaHide` 메뉴로 진입하여 설정을 진행합니다. Themida는 매우 강력한 탐지 기술을 사용하므로 다음 옵션들이 중요합니다.

### 3.1 권장 프로필 사용
가장 쉬운 방법은 미리 정의된 프로필을 사용하는 것입니다.
1.  **Profile** 드롭다운 메뉴 클릭.
2.  **"Themida x64"** (또는 "Themida/WinLicense") 선택.
3.  **Apply** -> **OK** 클릭.

### 3.2 주요 안티-디버그 옵션 설명 (Themida 관련)
ScyllaHide 옵션 창에서 체크되는 주요 항목들은 다음과 같습니다. (문서 3절 Features 참조)

#### 3.2.1 PEB (Process Environment Block) 보호
Themida가 가장 먼저 확인하는 메모리 구조체입니다.
*   **BeingDebugged**: 필수 체크. 디버거 존재 여부 플래그를 0으로 조작합니다.
*   **NtGlobalFlag**: 필수 체크. 디버깅 시 설정되는 힙 플래그를 숨깁니다.
*   **HeapFlags**: 필수 체크. 힙 생성 시 남는 디버그 흔적을 지웁니다. Themida가 이를 강력하게 검사합니다.

#### 3.2.2 NtSetInformationThread
*   **ThreadHideFromDebugger (0x11)**: 필수 체크. Themida는 이 API를 호출하여 중요한 스레드를 디버거로부터 숨기려고 시도합니다. ScyllaHide는 이 호출을 차단하여 디버거가 계속 스레드를 제어할 수 있게 합니다.

#### 3.2.3 NtQueryInformationProcess
*   **DebugPort / DebugFlags**: 프로세스가 디버깅 포트와 연결되어 있는지 확인하는 것을 막습니다.
*   **ProcessObjectHandle**: 디버그 객체 핸들 검사를 우회합니다.

#### 3.2.4 기타 보호
*   **BlockInput**: 키보드/마우스 입력을 차단하는 기능을 무력화하여, 디버깅 중 제어 불능 상태를 방지합니다.
*   **DRx Protection (Hardware Breakpoints)**: 하드웨어 브레이크포인트를 탐지하거나 지우는 시도를 막습니다. (필요 시 체크)

## 4. 실행 및 덤프 (Usage Workflow)

1.  **x64dbg 실행**: 관리자 권한으로 `x64dbg.exe` 실행.
2.  **옵션 확인**: `Plugins` -> `ScyllaHide` -> `Option`에서 `Themida` 프로필이 선택되었는지 확인.
3.  **파일 열기 (F3)**: `KakaoTalk.exe` 선택.
4.  **실행 (F9)**: 프로그램을 실행합니다. ScyllaHide가 탐지를 막아주므로 카카오톡 로그인 창이 정상적으로 떠야 합니다.
5.  **덤프 (Scylla)**:
    *   로그인 창이 뜬 상태(언패킹 완료)에서, x64dbg의 `Plugins` -> `Scylla` (Scylla는 덤프 도구, ScyllaHide와 다름) 실행.
    *   **Dump** 버튼 클릭하여 메모리 덤프 저장.
    *   **Fix Dump** 를 통해 IAT(Import Address Table) 복구 시도.

## 5. 문제 해결 (Troubleshooting)

*   **"Debugger Detected" 오류 발생 시**:
    *   ScyllaHide 옵션에서 `DRx Protection`을 켜거나 꺼보며 테스트하세요.
    *   x64dbg 설정에서 "System Breakpoint"에서 멈추지 않도록 설정해보세요.
*   **프로그램이 멈추거나 죽는 경우**:
    *   일부 Themida 버전은 `NtQuerySystemInformation` 후킹에 민감할 수 있습니다. 해당 옵션을 체크 해제해보세요.
    *   VMware 설정(`vmx`)에서 가상머신 탐지 우회 옵션(Hardening)이 적용되었는지 확인하세요. (ScyllaHide는 유저 모드만 방어하므로, VM 탐지는 별도 설정 필요)

## 6. 개발자 정보
*   본 툴은 NtQuery, cypher, mrexodia 등에 의해 개발되었습니다. (문서 5절)

# 6. x32dbg를 이용한 KakaoTalk(32bit) 메모리 덤프 가이드

## 1. 사전 준비
*   **x32dbg.exe**: 반드시 **관리자 권한**으로 실행해야 합니다.
*   **ScyllaHide (32-bit)**: `\x32\plugins\` 폴더에 `HookLibraryx86.dll` 등이 올바르게 설치되어 있어야 합니다.
*   **KakaoTalk**: 실행되어 있지 않아야 합니다 (완전히 종료 확인).

## 2. 상세 단계별 절차

### 1단계: x32dbg 설정 및 로드
1.  **x32dbg.exe**를 관리자 권한으로 실행합니다.
2.  상단 메뉴 **Plugins** -> **ScyllaHide** -> **Options** 진입.
3.  **Profile**에서 **"Themida x86"** (또는 Themida/WinLicense) 선택 후 **Apply** -> **OK**.
4.  키보드 **F3**을 누르거나 **File** -> **Open** 선택.
5.  `C:\Program Files (x86)\Kakao\KakaoTalk\KakaoTalk.exe` 경로를 찾아 엽니다.

### 2단계: 실행 및 언패킹 유도 (Themida Unpacking)
이 단계는 Themida가 스스로 코드를 메모리에 풀도록 유도하는 과정입니다.

1.  파일을 열면 x32dbg가 **System Breakpoint** (ntdll.dll 로드 시점 등)에서 멈춥니다.
2.  **F9 (Run)** 키를 누릅니다.
    *   **주의**: Themida가 중간에 예외(Exception)를 일으킬 수 있습니다.
    *   만약 하단 상태바에 "Exception..." 이라고 뜨면서 멈추면, **Shift + F9** (예외 무시하고 실행)를 계속 누르세요.
3.  **카카오톡 로그인 창이 화면에 뜰 때까지** F9 또는 Shift+F9를 반복합니다.
4.  **중요**: 카카오톡 **로그인 화면이 예쁘게 뜨면**, x32dbg로 돌아옵니다.
    *   이때 x32dbg는 "Running" 상태일 것입니다.
    *   **F12 (Pause)** 키를 눌러서 디버거를 **일시정지(Paused)** 상태로 만듭니다. (덤프를 뜨기 위해 멈추는 것)

### 3단계: Scylla를 이용한 메모리 덤프 (Scylla Dump)
메모리에 풀린 코드를 파일로 저장하는 핵심 단계입니다.

1.  상단 메뉴 **Plugins** -> **Scylla** 선택 (Scylla 창이 새로 뜹니다).
2.  **Attach to an active process** 목록에서 `KakaoTalk.exe`가 선택되어 있는지 확인합니다. (자동으로 잡혀있을 것입니다).
    *   *OEP (Original Entry Point)* 부분은 Scylla가 자동으로 찾으려 노력하지만, Themida는 이를 숨깁니다. 일단 기본값(현재 EIP 등)을 둡니다.
3.  **[Dump]** 버튼 클릭.
    *   저장 대화상자가 뜨면 `KakaoTalk_dump.exe` 라는 이름으로 바탕화면 등에 저장합니다.
    *   **Log 창 확인**: "Dump saved to..." 메시지 확인.

### 4단계: IAT 복구 (Import Address Table Fix)
덤프만 뜨면 함수(API) 연결이 끊어져서 실행도 안 되고 분석도 안 됩니다. IAT를 복구해야 합니다.

1.  Scylla 창의 하단 **IAT Info** 섹션을 봅니다.
2.  **[IAT Autosearch]** 버튼 클릭.
    *   "IAT found at..." 팝업이 뜨면 **[예(Yes)]**.
    *   *만약 실패하면 "IAT Start" 주소를 수동으로 찾아야 하지만, Themida 프로필이 켜져 있다면 보통 찾습니다.*
3.  **[Get Imports]** 버튼 클릭.
    *   왼쪽 리스트에 `kernel32.dll`, `user32.dll` 등 수입 함수 목록이 쫘르륵 떠야 합니다.
    *   **중요**: 만약 리스트에 **빨간색 X 표시(Invalid)**가 너무 많다면, Themida가 API를 심하게 꼬아놓은 것입니다. (이 경우 ScyllaHide 옵션을 조절하며 다시 시도해야 함). 초록색 체크가 많다면 정상입니다.
4.  **[Fix Dump]** 버튼 클릭.
    *   방금 3단계에서 저장했던 `KakaoTalk_dump.exe` 파일을 **선택**합니다 (열기).
    *   Scylla가 해당 파일을 수정하여 `KakaoTalk_dump_SCY.exe` (SCY 접미사 붙음) 파일을 새로 생성합니다.

### 5단계: 결과 확인
1.  `KakaoTalk_dump_SCY.exe` 파일이 생성되었는지 확인합니다.
2.  이 파일을 **Ghidra**에 넣고 분석을 돌립니다.
3.  Ghidra의 "Symbol Tree" -> "Imports" 항목을 봤을 때, `CreateFile`, `InternetOpen` 같은 함수 이름들이 보인다면 **성공**입니다.

## 요약 체크리스트

# 7. 덤프된 바이너리 1차 분석 보고서

## 1. 개요
ScyllaHide를 통해 덤프된 `KakaoTalk_dump_SCY.exe` 파일을 Ghidra에 로드하여 초기 분석을 수행했습니다.

## 2. 분석 결과 (Status)

### 2.1 메모리 맵 (Memory Map)
바이너리는 성공적으로 로드되었으며, 섹션 구조는 정상적인 32-bit PE 파일의 형태를 띠고 있습니다.
*   **Base Address**: `0x00400000`
*   **Code Section (.text)**: `0x00401000` ~ `0x02193fff` (약 30MB)
*   **Import Data (.idata)**: `0x02bfe000` 영역에서 `WINHTTP.dll` 등의 흔적이 확인됨.

### 2.2 문제점 (Issue)
**자동 분석 실패**: Ghidra가 코드 영역(`0x00401000`)을 자동으로 "함수"로 인식하지 못했습니다.
*   **원인**: Themida 해제 후 OEP(진입점)가 `0x03e09058`로 설정되어 있는데, 이는 표준 코드 섹션 바깥입니다. 이로 인해 Ghidra의 자동 분석기가 메인 코드 섹션을 건너뛰고 "데이터"로 취급하고 있습니다.
*   **증상**: 문자열 검색(String Search)이나 함수 목록(Function List)이 비어있거나 시스템 함수만 보입니다.

## 3. 조치 방법 (Action Required)

Ghidra의 **[CodeBrowser]** 창 중앙에 있는 **「Listing」 화면**(주소와 16진수 코드가 보이는 곳)에서 진행해야 합니다.

1.  **코드 섹션 이동**:
    *   **Listing 화면**을 클릭하여 포커스를 둡니다.
    *   **Go To** (`G` 키)를 누릅니다.
    *   주소 `00401000` (또는 `0x401000`)을 입력하고 엔터.
2.  **디스어셈블 (Disassemble)**:
    *   `00401000` 주소의 데이터가 보일 것입니다 (아마도 `55 8B EC...` 등으로 시작할 가능성이 높습니다).
    *   해당 위치에 커서를 두고 키보드 **`D`** 키를 누릅니다.
    *   데이터가 어셈블리 코드(`PUSH EBP`, `MOV EBP, ESP` 등)로 변하는지 확인합니다.
3.  **함수 생성 (Create Function)**:
    *   코드로 변한 영역 선택 후 키보드 **`F`** 키를 눌러 함수(`FUN_00401000`)로 만듭니다.
    *   Ghidra가 자동으로 연결된 코드들을 따라가며 분석을 시작할 것입니다 (우측 하단 분석 게이지 확인).

## 4. 향후 분석 계획 (Next Steps)
위 조치를 통해 코드가 보이기 시작하면 다음 항목들을 찾을 것입니다.
*   **문자열**: "LOCO", "Login", "kakao.com"
*   **API**: `WinHttpSendRequest`를 호출하는 함수 (로그인 네트워크 로직)
*   **암호화**: AES / RSA 관련 상수 및 로직

분석이 완료되면 이 보고서를 업데이트하겠습니다.

## 5. 트러블슈팅: Stolen Bytes 문제 (코드 깨짐 현상)

**증상**: `00401000`에서 함수를 만들었으나, 코드가 `DEC ECX` 등 의미 없는 명령어로 보입니다.
**원인**: Themida 패커가 프로그램의 시작 부분(OEP) 코드를 훔쳐서 다른 곳에 숨겨두었기 때문입니다 (**Stolen Bytes**).

**해결책**:
시작 부분은 무시하고, **프로그램의 중간(정상적인 코드 영역)**으로 직접 점프해야 합니다. 가장 확실한 방법은 **문자열 검색**입니다.

### [필수] 문자열로 코드 찾기
1.  Ghidra 상단 메뉴 **Search** -> **For Strings...** 클릭.
2.  **[Search]** 버튼 클릭.
3.  검색 결과 창(Strings)이 뜨면 Filter 입력란에 `LOCO` 입력.
4.  결과 중 하나를 더블클릭하여 이동.
5.  이동한 곳 주변의 회색 바이트들을 클릭하고 **`D`**(디스어셈블) -> **`F`**(함수 생성).

# 8. 분석 전략 전환 보고서: 정적 분석 -> 동적 분석

## 1. 현황 및 문제점
덤프된 바이너리(`KakaoTalk_dump_SCY.exe`)를 정적 분석한 결과, **Themida의 강력한 난독화(Obfuscation)**가 여전히 남아있음을 확인했습니다.

*   **문제 1: Stolen Bytes**: 실제 코드 영역(`0x401000`)의 명령어가 훼손되어 읽을 수 없습니다.
*   **문제 2: 문자열 암호화**: "LOCO", "Login" 등의 핵심 문자열이 평문으로 보이지 않습니다. (Ghidra 검색 실패)
*   **문제 3: 가상화(Virtualization)**: Entry Point(`0x3e09058`)가 일반 코드가 아닌, Themida의 가상 머신(VM) 영역(`0x03e0...`)을 가리키고 있습니다.

즉, **"덤프는 되었으나, 코드는 여전히 읽기 힘든 상태"**입니다. 이를 억지로 복구(Deobfuscation)하려면 수 주 이상의 시간이 소요됩니다.

## 2. 전략 변경: 동적 후킹 (Dynamic Hooking)
우리의 목적은 "로그인 패킷 내용을 보는 것"입니다. 코드를 다 읽을 필요 없이, **프로그램이 OS(윈도우)에 통신을 요청하는 순간**을 덮치면 됩니다.

Themida도 결국 인터넷을 쓰려면 윈도우 API인 `WINHTTP.dll`을 호출해야 합니다. 이는 숨길 수 없습니다.

### 변경된 계획
1.  **Ghidra 분석 중단**: 현재 상태로는 효율이 너무 떨어지므로 보류합니다.
2.  **Frida 도입**: 실행 중인 카카오톡에 침투하여 API를 감시하는 도구입니다.
3.  **API 후킹**:
    *   `WinHttpSendRequest`: 요청을 보낼 때 가로챕니다.
    *   `WinHttpWriteData`: 실제 로그인 데이터(LOCO JSON 등)가 담기는 곳입니다.
4.  **데이터 추출**: 후킹된 시점의 메모리를 읽어 아이디/비번/토큰 값을 확보합니다.

## 3. 결론
"깨진 자물쇠(덤프 파일)를 고치려 하지 말고, 문이 열릴 때(API 호출) 옆에서 지켜보는 것"이 훨씬 빠릅니다.
**Frida를 이용한 라이브 후킹** 단계로 넘어갈 것을 제안합니다.

# 9. LOCO 프로토콜 및 로그인 패킷 구조 분석

## 1. 개요
본 문서는 Frida 메모리 스캔(`hook_scan_v2.js`)을 통해 획득한 카카오톡 PC 버전의 로그인 패킷 구조와 핵심 인증 값을 분석한 결과를 정리한다.
카카오톡은 `WinSock`을 통해 TLS 암호화 통신을 수행하며, 암호화 직전 메모리에 `x-www-form-urlencoded` 형태의 평문 데이터를 생성함을 확인하였다.

## 2. 로그인 패킷 구조 (Login Packet Structure)
획득한 메모리 덤프(`hook_scan_v2_result.txt`) 분석 결과, 로그인 패킷은 JSON이 아닌 **HTTP Query String** 형식을 따른다.

### 2.1 전체 형태
```text
email={EMAIL}&password={PASSWORD}&device_uuid={DEVICE_UUID}&...
```

### 2.2 필드 상세
| 필드명 | 예시 데이터 (일부 마스킹) | 설명 |
| :--- | :--- | :--- |
| `email` | `theman****%40gmail.com` | 사용자 ID (URL Encoded) |
| `password` | `test1234` | 사용자 비밀번호 |
| `device_uuid` | `supnx3Mu0HpG9br...` | **[핵심]** 기기 고유 식별자 (Base64) |
| `client_version` | (불명/추정) | 클라이언트 버전 정보 (dump 주변 데이터 참조 필요) |
| `os_version` | (불명/추정) | OS 정보 |

> **참고**: `device_uuid`는 카카오톡 서버가 해당 PC를 "인증된 기기"로 식별하는 핵심 키(Key)이다. 이 값은 레지스트리나 로컬 파일에 저장된 값을 읽어와 생성되는 것으로 추정된다.

## 3. 기기 식별자 (Device UUID) 분석
획득한 `device_uuid` 값은 Base64로 인코딩되어 있으며, 디코딩 시 바이너리 데이터 또는 특정 해시 값일 가능성이 높다.

- **Raw Value**:
  ```text
  supnx3Mu0HpG9brcqZukaAaPxkbBRuSe7WkG1lYzDDyaawfIrMjtA5dlI0Loeb%2BdBm%2F9CJmmCzDOqs4fdiIog%3D%3D
  ```
- **URL Decoded**:
  ```text
  supnx3Mu0HpG9brcqZukaAaPxkbBRuSe7WkG1lYzDDyaawfIrMjtA5dlI0Loeb+dBm/9CJmmCzDOqs4fdiIog==
  ```

## 4. 향후 활용 계획 (Action Plan)
이 분석 결과를 바탕으로 Python 기반의 "로그인 에뮬레이터"를 제작하여 웹 클라이언트 구현 가능성을 검증한다.

1.  **로그인 테스트 스크립트 작성**: `python_login_test.py`
    - `requests` 또는 `socket` 라이브러리 사용.
    - 위에서 파악한 `device_uuid`를 고정값으로 사용하여 로그인 요청 전송.
2.  **응답 분석**:
    - 성공 시: `access_token`, `refresh_token` 등 세션 정보 획득 확인.
    - 실패 시: 추가 필드(헤더, 쿠키 등) 필요 여부 확인.

## 5. 결론
Themida 난독화로 인해 정적 분석이 불가능했던 "기기 인증값"을 동적 메모리 스캔을 통해 성공적으로 추출하였다. 이는 `KakaoWebTalk` 프로젝트의 핵심 난관을 돌파한 것으로 평가된다.
