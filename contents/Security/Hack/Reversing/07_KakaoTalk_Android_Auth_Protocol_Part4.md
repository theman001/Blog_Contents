## 0. 네이티브 암호화 계층 접근
3편에서는 JNI 구조와 네이티브 라이브러리 분석을 통해  
기기 인증과 관련된 핵심 로직이 자바 레이어가 아닌  
`libtalkand_aes.so` 내부에 존재함을 확인했다.

이번 편에서는 해당 라이브러리의 암호화 구현을 직접 분석하여,

- 사용 중인 암호 알고리즘
- 하드코딩된 Key 및 IV 존재 여부
- Device-Info 헤더 내부 암호화 토큰의 실체

를 단계적으로 정리한다.

---

## 1. 암호 알고리즘 식별 방법
바이너리 레벨에서 암호 알고리즘을 식별할 때  
가장 효과적인 방법 중 하나는 **고유 상수(Constants)** 탐색이다.

AES 계열 알고리즘은 내부적으로 고정된 S-Box 테이블을 사용하며,  
다음과 같은 상수 패턴을 가진다.

```text
63 7c 77 7b f2 6b 6f c5 30 01 67 2b fe d7 ab 76
```
Ghidra의 메모리 검색 기능을 통해  
해당 S-Box 패턴을 추적한 결과,  
`0x0001db54` 인근에서 AES 관련 연산 루틴이 확인되었다.

---

## 2. AES-256-CBC 구현 확인
S-Box 사용, 블록 크기(16바이트),  
라운드 키 확장 로직을 종합적으로 분석한 결과  
해당 구현은 다음과 같은 특징을 가진다.

- **알고리즘**: AES-256
- **운영 모드**: CBC (Cipher Block Chaining)
- **패딩 방식**: PKCS#7
- **구현 위치**: `Java_com_kakao_talk_aes_TalkHello_encrypt`

이 함수는 JNI를 통해 자바 레이어에서 직접 호출되며,  
인증 및 기기 정보 관련 데이터 암호화에 사용된다.

---

## 3. 하드코딩된 Key 및 IV 추출
분석 과정에서 가장 중요한 부분은  
암호화에 사용되는 **Key와 IV가 외부 입력이 아닌,  
네이티브 코드 내부에 상수 형태로 존재**한다는 점이다.

### 3.1 추출 결과 (v11.3.0 기준)
해당 값들은 리틀 엔디언(Little Endian) 형태로 저장되어 있었으며,  
다음과 같이 복원되었다.

**AES-256 Key (Hex)**  
```text
d317b436ed44dd2a47c65ba922ea39c017fb40b32d5c27f43add51cf49f15ac4
```
**Initialization Vector (IV)**  
```text
b46ca0c59ae4aa0adf2f3c57286470ab
```
이 값들은 실행 환경이나 단말에 따라 변경되지 않는  
**정적 암호화 상수**로 확인되었다.

---

## 4. uvc3 토큰 복호화 분석
Key와 IV를 확보한 후,  
`Device-Info` 헤더에 포함되어 있던 암호화 토큰 **`uvc3`**를  
동일한 AES-256-CBC 로직으로 복호화했다.

복호화 결과는 JSON 구조의 데이터였으며,  
다음과 같은 정보가 포함되어 있었다.

```json
{
  "apkChecksum": "MlfVmaSdLJ...",
  "installReferrer": "utm_source=google-play...",
  "batteryPct": 100,
  "cpuName": "Kalama",
  "totalMemory": 11162484736,
  "sims": [{"tpn_eq_sim": 1, "operator": "45005"}]
}
```


### 4.1 uvc3의 역할
`uvc3`는 단순 식별 토큰이 아니라,

- APK 무결성 정보
- 설치 경로
- 배터리 상태
- CPU 및 메모리 정보
- SIM/통신사 정보

등을 포함한 **기기 텔레메트리 데이터**임이 확인되었다.

서버는 이 데이터를 복호화하여  
요청을 보낸 클라이언트가 실제 단말 환경인지,  
혹은 에뮬레이션·자동화 환경인지 판단하는 것으로 보인다.

---

## 5. 재현 시도와 한계
확보한 암호화 로직과 Key·IV를 기반으로  
Python 환경에서 동일한 암호화 과정을 구현하고  
기기 등록 요청을 재시도했다.

그러나 결과는 변하지 않았다.

- HTTP 응답: `200 OK`
- 내부 상태 코드: `status: -500`

이는 암호화 로직 자체는 재현되었지만,  
**암호화 대상이 되는 실제 데이터 값이  
서버 측 검증 조건을 만족하지 못했을 가능성**을 의미한다.

---

## 6. 정리
4편에서 확인한 핵심 내용은 다음과 같다.

- `libtalkand_aes.so`는 AES-256-CBC 암호화를 사용함
- Key와 IV는 네이티브 코드 내부에 하드코딩되어 있음
- `uvc3`는 기기 상태 및 환경을 상세히 담은 텔레메트리 데이터
- 암호화 구현 자체보다, **데이터의 현실성**이 서버 검증의 핵심 요소임

정적 분석을 통해 암호화 구조는 확보했지만,  
실제 서비스 환경에서 생성되는 데이터의 특성을  
완전히 재현하는 단계로 넘어가야 함이 분명해졌다.
