## 개요

이 글은 **Blog Project** 시리즈의 다섯 번째 글로,  
이 블로그에서 **게시글을 어떻게 관리하고, 프론트엔드와 분리된 구조로 운영하는지**를 정리한다.

핵심 주제는 다음 한 문장으로 요약된다.

> **“콘텐츠는 코드와 분리하고, 블로그는 Headless CMS처럼 동작한다.”**

---

## 왜 게시글을 코드에서 분리했는가

블로그를 설계하면서 가장 먼저 내린 결정 중 하나는  
**게시글을 프론트엔드 코드와 함께 두지 않겠다는 것**이었다.

그 이유는 단순하다.

- 글을 쓸 때마다 프론트엔드 코드를 만지고 싶지 않았다
- UI 수정과 콘텐츠 작성을 독립적으로 진행하고 싶었다
- 글은 “데이터”로 취급하는 편이 관리하기 편했다

즉,  
이 블로그에서 프론트엔드는 **뷰어(Viewer)**이고,  
게시글은 **외부에서 공급되는 콘텐츠**다.

---

## 전체 구조 요약

게시글 관리 구조는 **두 개의 물리적인 영역**과  
그에 따른 **역할 분리**를 기준으로 설계되어 있다.

### 1. 작성 영역 (`contents`)
- 실제 게시글을 작성하는 공간
- Markdown(`.md`) 파일 형태로 관리
- Front Matter와 본문을 포함한 **원본 콘텐츠 저장소**
- Git 기반으로 버전 관리됨

### 2. 저장 영역 (`script`)
- `contents` 디렉토리의 Markdown 파일을 기준으로
- 메타데이터와 본문을 파싱하여
- **NeonDB와 동기화**하는 스크립트 영역
- 게시글을 “데이터베이스 레코드”로 변환하는 역할을 담당

이 두 영역은 다음과 같은 관계를 가진다.

- `contents`는 **사람이 읽고 쓰는 영역**
- `script`는 **시스템이 처리하는 영역**
- 두 영역은 직접 의존하지 않고,  
  동기화 과정을 통해서만 연결된다

이를 통해,

- 글 작성 방식은 최대한 단순하게 유지하면서
- 저장 구조와 서비스 구조는 독립적으로 확장할 수 있도록 설계했다.

---

## 1. 게시글 작성: Markdown 파일

게시글은 항상 **Markdown 파일**로 작성한다.

- 로컬 환경에서 작성
- Git으로 버전 관리
- 에디터나 플랫폼에 종속되지 않음

Markdown 파일에는 다음 정보가 포함된다.

- Front Matter (제목, 태그, 날짜 등)
- 본문 콘텐츠
- 코드 블록, 인용, 리스트 등 구조적 요소

이 단계까지는  
**일반적인 기술 블로그 작성 방식과 크게 다르지 않다.**

---

## 2. 콘텐츠 저장소 분리

작성된 Markdown 파일은  
**게시글 전용 Git Repository**에서 관리된다.

이 레포지토리는 다음 목적을 가진다.

- 콘텐츠 이력 관리
- 글 수정 내역 추적
- 프론트엔드 코드와 완전 분리

즉,  
“블로그 글 저장소”와  
“블로그 UI 코드 저장소”는 서로 다른 책임을 가진다.

---

## 3. DB 동기화 개념

Markdown 파일은 그대로 서비스되지 않는다.  
중간에 **DB 동기화 단계**가 존재한다.

개념적인 흐름은 다음과 같다.

1. Markdown 파일이 커밋됨
2. 변경 사항을 감지
3. Front Matter와 본문 파싱
4. DB에 Insert 또는 Update

이 과정은 자동화 도구(CI/CD 또는 스크립트)를 통해 처리된다.

---

## NeonDB를 선택한 이유

게시글 저장소로 **NeonDB (PostgreSQL 기반 Serverless DB)**를 사용했다.

선택 이유는 다음과 같다.

- 서버리스 구조로 관리 부담이 적음
- PostgreSQL 기반이라 구조 설계가 명확함
- 읽기 중심 워크로드에 적합
- 프론트엔드에서 API 형태로 접근 가능

블로그 규모에서는  
“과한 설정 없이 안정적으로 쓸 수 있다”는 점이 가장 컸다.

---

## DB 스키마 설계

게시글 테이블은 최대한 단순하게 구성했다.

- `id`: Primary Key
- `title`: 게시글 제목
- `slug`: URL 식별자
- `content`: Markdown 본문
- `category`: 카테고리
- `created_at`: 작성일

이 구조의 핵심은  
**프론트엔드가 필요한 정보만 갖고 있다는 것**이다.

- 렌더링에 필요한 최소 필드만 유지
- UI 변경 시 DB 수정 최소화
- 검색, 정렬 확장이 쉬움

---

## 프론트엔드에서의 사용 방식

SPA 프론트엔드는  
DB를 “글 저장소”로만 인식한다.

- 게시글 목록 조회
- 특정 slug의 게시글 조회
- 받은 Markdown을 렌더링

프론트엔드는:

- 글이 어디서 작성됐는지
- 어떻게 관리되는지

를 알 필요가 없다.

이로써,  
**프론트엔드와 콘텐츠 관리의 완전한 분리**가 이루어진다.

## Headless CMS 구조에 가까운 이유

이 구조는 전통적인 CMS와 다르다.

- 관리자 UI ❌
- 웹 기반 편집기 ❌
- 권한 관리 ❌

하지만 개념적으로는,

- 콘텐츠는 외부에서 관리되고
- 프론트엔드는 API로 소비하며
- 표현은 전적으로 클라이언트 책임

이라는 점에서  
**Headless CMS와 매우 유사한 구조**를 가진다.

---

## 이 구조의 장점

- 콘텐츠와 UI 완전 분리
- 글 작성 흐름이 단순함
- 프론트엔드 변경 부담 감소
- 확장성 (검색, 태그, SEO 대응 용이)

블로그 운영의 중심이  
“기능 유지”가 아니라 **기록과 정리**에 맞춰진다.
