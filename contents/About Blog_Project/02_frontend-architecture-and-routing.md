## 개요

이 글은 **Blog Project** 시리즈의 두 번째 글로,  
이 블로그의 **프론트엔드 아키텍처와 SPA 라우팅 구조**를 중심으로 정리한다.

외부 프레임워크 없이 순수 HTML / CSS / JavaScript만으로  
어떻게 **Single Page Application 구조**를 구성했고,  
왜 이런 방식이 블로그라는 서비스 성격에 맞다고 판단했는지를 기록한다.

## 전체 구조 개관

이 블로그는 **Client-Side Rendering(CSR)** 기반의 SPA이다.

- 서버는 정적 파일만 제공
- 페이지 전환은 브라우저 새로고침 없이 JS로 처리
- URL은 실제 페이지처럼 유지
- 콘텐츠는 동적으로 불러와 렌더링

즉, **“정적 웹 + SPA 라우팅”** 구조다.

---

## SPA 진입점: index.html

모든 요청의 시작점은 `index.html`이다.

- 실제로는 하나의 HTML 파일만 존재
- 어떤 URL로 접근하더라도 동일한 파일이 로드됨
- 이후의 화면 구성은 전부 JavaScript의 역할

이 방식의 장점은 명확하다.

- 서버 설정이 단순함
- Cloudflare Pages 같은 정적 호스팅과 궁합이 좋음
- 배포 파이프라인이 가벼움

---

## 라우터 설계 개요

라우팅은 `assets/js/router.js`에서 담당한다.

핵심 개념은 다음과 같다.

- URL 경로(`location.pathname`)를 기준으로
- 해당 경로에 대응하는 **Page 모듈**을 선택
- 선택된 모듈을 동적으로 로드하여 화면을 교체

라우터는 프레임워크의 복잡한 상태 관리 없이,  
**URL → Page 매핑**이라는 최소한의 역할만 수행한다.

---

## History API 기반 라우팅

브라우저의 `History API`를 사용하여 SPA 라우팅을 구현했다.

- `pushState`로 URL 변경
- `popstate` 이벤트로 뒤로가기/앞으로가기 처리
- 실제 페이지 이동 없이 화면만 교체

이 덕분에,

- 주소창 URL은 항상 실제 페이지처럼 보이고
- 북마크 / 새로고침 / 직접 접근이 가능하며
- 사용자 입장에서는 일반 웹사이트와 차이가 없다

---

## Page 모듈 구조

각 페이지는 `pages/` 디렉토리 아래 **독립적인 JS 모듈**로 존재한다.

- `home.js` → 메인 / 카테고리 목록
- `post.js` → 게시글 상세 페이지
- `hidden.js` → XP 테마 이스터에그 페이지

각 Page 모듈은 공통적으로 다음 책임을 가진다.

- 필요한 데이터 요청
- 데이터 가공 (Markdown → HTML 등)
- `#main-content` 영역에 렌더링

라우터는 **“어떤 페이지를 보여줄지”만 결정**하고,  
**“무엇을 어떻게 그릴지는 Page가 책임”**지는 구조다.

---

## 동적 Import와 코드 분리

페이지 로딩 시 모든 JS를 한 번에 불러오지 않는다.

- 현재 URL에 필요한 Page만 `import()`
- 나머지는 실제로 접근하기 전까지 로드하지 않음

이 방식은 결과적으로 다음 효과를 준다.

- 초기 로딩 리소스 감소
- 페이지 수가 늘어나도 구조가 유지됨
- “블로그 + 기능 페이지” 혼합 구조에 유리

규모는 작지만, **확장 가능한 구조를 유지하기 위한 선택**이다.

---

## CSR 구조를 선택한 이유

이 블로그는 **콘텐츠 중심의 정적 웹 포스팅**이 목적이다.

- 실시간 상호작용이 많은 서비스 아님
- SEO는 구조적 개선으로 대응 가능
- 서버 렌더링이 필수적인 요구사항 없음

CSR 기반 SPA 구조는,

- 정적 호스팅 환경에서 가장 단순하고
- 운영 부담이 적으며
- UI 확장과 실험에 유리하다

블로그라는 서비스 성격에 비추어 보았을 때,  
**과한 복잡성 없이 충분한 기능을 제공하는 구조**라고 판단했다.

---

## 이 구조의 장단점

### 장점

- 서버 관리 부담 최소화
- 배포 구조 단순
- UI/UX 실험에 자유로움
- 코드 흐름을 직접 통제 가능

### 단점

- 초기 SEO 대응이 필요
- 모든 렌더링을 클라이언트가 담당
- 구조가 커지면 규칙 관리가 중요해짐

이 단점들은 이후 글에서  
**SEO 전략, 검색 기능, 구조 개선**을 통해 하나씩 다룰 예정이다.
